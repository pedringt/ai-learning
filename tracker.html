Open questions for the PMQuestions 1–12 + simulated answers/resolutions

Meridian is a fictional practice scenario — nothing here is a real company or real data. These are questions I thought of while working through the exercise, logged as I raised them. Where I didn't want to stall out waiting on an answer, I made up a plausible simulated one (clearly marked) so I could keep practicing the reasoning.

1 · TargetsAre there existing target numbers from Meridian leadership, or should I propose targets based on restoring pre-growth performance (response time <2 hrs, CSAT 91%)? We don't appear to have a pre-growth AHT number to anchor to.
Simulated answer: No formal targets set yet — this pilot is intentionally scoped to let CS propose data-driven targets rather than lock in commitments early. Pre-growth numbers are a reasonable long-term north star, not a hard pilot deadline.
Resolution: validated the approach already taken — propose defensible pilot targets, treat pre-growth numbers as the long-term aim.
2 · Knowledge baseWhat is the process for updating the knowledge base? ~20% of the ~180 articles are unreviewed in 12+ months with conflicting/outdated guidance — this could realistically block the pilot if not addressed first.
Simulated answer (harder): No formal review process, and no bandwidth to prioritize one before launch — leadership wants to hold the 8-week timeline given the enterprise renewal pressure. Deal with KB issues as they come up.
Resolution: accepted the timeline, but built in a mitigation — explicitly track failures caused by stale/conflicting KB content as a distinct root-cause category during VALIDATE/troubleshooting (ties to the guide's own RAG-troubleshooting framework), rather than letting the risk go unmonitored. Separately seeded a future EXPAND-stage idea: a KB-cleanup/maintenance agent — intentionally held back until pilot data shows it's actually worth recommending, not proposed prematurely.
3 · Escalation scenariosDo we have a complete list of human-boundary/escalation scenarios, or just the examples in the handoff (refunds, credits, disputes, password resets, account changes, security actions)?
Simulated answer: That's the full formally-agreed list so far, but no deep audit has been done. If something ambiguous comes up during the pilot, use judgment in the moment and flag it afterward.
Resolution: pushed back to confirm the list is actually complete, and built in a default-to-escalate rule for anything ambiguous, with the rule open to revision if it starts over-escalating harmless cases.
4 · Workflow modelDo Tier 1 reps handle tickets start-to-finish before moving to the next one, or do they send a quick first-touch acknowledgment and return later for full resolution? This changes how much first-response time can realistically improve if AHT doesn't.
Simulated answer: Mixed model — most reps handle tickets start-to-finish, but on high-volume days they'll send a quick first-touch acknowledgment on lower-priority tickets to keep queue wait down, then circle back for full resolution.
Resolution: informed the first-response-time target (see Success Measurement Plan below) and the timestamp-based proxy metric.
5 · Draft scopeFor higher-risk categories (account access, money-related), does the AI still draft a response for human review — just flagged for extra scrutiny — or does it skip drafting entirely and escalate straight to a human?
Simulated answer (harder): Undecided — engineering flagged that AI-drafting anything for refund/credit categories creates a paper-trail/bug risk (e.g. accidental auto-send); legal hasn't weighed in. Make a recommendation with reasoning.
Resolution: recommended skipping drafting entirely for these categories for now — route straight to a human, no AI involvement — pending a firm answer from legal. Noted: if legal later clears drafting, these categories need to be added back into the Quality/Human intervention scope, which currently excludes them (see below).
6 · Pause authorityWho has the authority to pause the pilot (or a specific ticket category) if a guardrail is breached — is that me, my manager, or someone else? Needs to be defined before a real breach happens, not after.
Simulated answer: Category-level pauses don't need approval — go ahead. Full-pilot pauses need PM sign-off, though the PM may not always be reachable within a 24-hour window.
Resolution: covers category-level pauses. Full-pilot-pause gap led directly to open question 8.
7 · System data capabilityDoes Meridian's current help desk tool tag/distinguish a quick first-touch acknowledgment from a full ticket resolution — or is there a status field we could repurpose for this?
Simulated answer (curveball): There's an optional "Acknowledged" vs. "Resolved" status field, but it's inconsistently used — the data exists in theory but isn't reliable as-is.
Resolution: ran a "dev pushback" exercise — rather than requiring reps to remember an optional field, use two hard system timestamps that already exist for every ticket (first-reply-sent, resolved/closed) with no new instrumentation or rep behavior change needed. See First-response time target below for the resulting proxy metric.
8 · Backup pause contactIf the PM is unreachable and I believe the full pilot needs to be paused, who's my backup escalation contact?
Simulated answer: Go to the Engineering Lead first (can technically disable the pilot integration), and loop in the Director of Support Ops in parallel. Don't wait for both to respond if it's urgent — pause first, explain after.
Resolution: gives a real chain of authority and explicit permission to act before getting a response if urgent.
9 · Data/measurement ownershipWho sets up the actual tracking/instrumentation for these metrics — do I build it, or does someone else?
My own proposed answer (not simulated — this is my judgment call, not a PM fact): A developer/data team would own building the logging/instrumentation, based on a spec I write defining exactly what needs to be tracked (ticket category, draft vs. final, edit type, timestamps, escalation reason, etc.). I'd want raw data delivered to me rather than a pre-built dashboard, so I own turning it into the reviewable pilot report and interpreting it against the Success Measurement Plan. I'd also ask for direct access to Meridian's existing analytics/metrics tooling if I don't already have it.
10 · AHT baseline reliabilityDoes the 12.4 min AHT baseline already reflect a mix of one-shot and two-step (first-touch-then-resolve) tickets, and is it still a valid comparison point going forward?
Simulated answer: Unknown — the 12.4 min figure came from the help desk tool's built-in average, which doesn't currently distinguish workflow type. Probably some blend of both, and there's no clean way to separate it retroactively.
Resolution: keep 12.4 min as the working reference baseline for now (not worth forcing a retroactive fix), but track the new split data going forward for better-informed comparisons later.
11 · Baseline exchange countDoes Meridian already track average replies/exchanges per ticket, to inform a back-and-forth escalation threshold?

Rep discovery findings (simulated) & decisions madeQuestions 13–17 + what changed

These findings directly shaped the agent logic in the System Flow (escalation triggers, retrieval approach) and the pilot targets in the Measurement Plan (first-response time).

New escalation trigger added: customer explicitly asks for a supervisor or to escalate — a cleaner signal than inferring "upset" or counting exchanges, since it doesn't require interpretation.

Workflow model corrected: additional simulated rep input shows only 2 of 8 reps occasionally do a quick first-touch ack; most resolve start-to-finish. This is more reliable than the earlier simulated PM answer, since reps report their own actual behavior.
Changed my mind: revised the First-response time pilot target from ~6 hrs down to ~7 hrs (see below) after realizing the original target partly relied on a "distinct first-touch speedup" mechanism that barely applies if most tickets are one-shot. AHT and first-response are more entangled than originally assumed, though not identical — AI still saves composition time even in one-shot tickets, just less dramatically than first assumed.

KB remediation cadence: rather than a full pre-launch audit (not prioritized by leadership) or passive monitoring only, decided on an active/reactive process — when a pilot failure is traced to stale/conflicting KB content, that specific article gets fixed during the pilot, triggered by the failure itself.

Tool access: want a full inventory of tools reps use beyond the KB, to make sure the agent has access to what it actually needs — raised as open question 13 for the PM/build team.

Deeper dig — copy-paste: mostly reps pulling account/subscription/billing status from a separate billing system into the ticket, not the AI's draft going elsewhere. Means even "standard" category tickets may need billing/account context the AI doesn't currently have.

Deeper dig — KB search: both a content problem (duplicate/conflicting articles, already known) and a retrieval problem (basic keyword matching, no fuzzy/synonym support). The AI-assisted workflow does not have to inherit the current search limitation, but semantic search alone is not automatically the answer. The retrieval design should be tested against Meridian’s actual query set and may combine semantic and keyword retrieval, metadata filters, reranking, or simpler context injection. The content half still needs the reactive KB-fix process above.
Revised decision: evaluate a hybrid retrieval approach rather than assuming semantic search should replace keyword matching. Choose the simplest design that performs reliably on representative Meridian queries.

17 · Plan tier differencesWhat specifically varies between Meridian's plan tiers — and does the monthly analytics report feature vary by tier, or is it universal? Before assuming a given how-to question is config-dependent, need to know which features actually differ.

Keeps the original case as a true core/simple case, and creates a clear next case to test the actual config-dependent path.

AHT — pilot target

Target: Hold roughly steady during pilot — don't make it worse.
Reasoning: Mandatory human review of every AI draft caps how much time can actually be saved this phase — fact-checking an answer isn't dramatically faster than answering it in some cases. Any post-pilot change would mean selective automation only for low-risk, well-supported ticket types that earn it through eval and pilot evidence—not removing review broadly. Meaningful AHT reduction may become more realistic for that narrow eligible subset.
Changed my mind: I initially leaned toward proposing a meaningful AHT reduction alongside the other targets. Working through what "human review" actually requires (reading + fact-checking every draft) made me realize that time savings there are limited this phase — so I separated it from first-response time instead of treating both the same way.

First-response time — pilot target

Target: ~7 hrs blended (down from >8 hrs) — revised down from an earlier ~6 hr estimate. Tracked via two existing system timestamps rather than any new manual tagging.
Reasoning: AI drafting a response the moment a ticket arrives removes the "compose from scratch" step before a human ever opens the ticket, which should modestly raise throughput and pull down queue/backlog wait — even for one-shot tickets, since composition happens before a human is involved at all.
Measurement approach (resolved via open question 7): Use two hard timestamps every ticket already has — first-reply-sent and resolved/closed — instead of relying on reps remembering to update an optional status field. Gap between the two timestamps: < 20 minutes = one-shot resolution (buffer above the 12.4 min AHT baseline to avoid misclassifying normal variance); > 20 minutes = true two-step case (quick ack, resolved later). This gives the first-touch-vs-full-resolution split without needing any new rep behavior or instrumentation.
Proposed refinement, tested against a simulated "dev pushback": originally planned to require reps to tag each ticket's workflow type, but a dev flagged that optional-turned-required fields are often forgotten. The timestamp-gap proxy solves the same problem without depending on human compliance.
Changed my mind (again): the original ~6 hr target assumed a meaningful "mixed workflow" — some tickets getting a distinct, extra-fast first-touch ack separate from full resolution — per the simulated PM answer to question 4. Rep discovery (simulated) showed this is rare — only 2 of 8 reps do it occasionally. Since I'd trust reps' account of their own actual behavior over the PM's secondhand description, revised the target down to ~7 hrs: still a real improvement (throughput still rises since composition time is saved even in one-shot tickets), but more modest than originally assumed, and closer in spirit to the AHT reasoning (capped by the same human-review bottleneck) than treated as fully independent.

Quality — pilot target

Target: ≥ 80% of AI drafts approved with no substantive edit needed (trivial tone/formatting edits don't count against this).
Reasoning: Quality is a launch/scale gate — it's what justifies loosening the mandatory-review requirement later — so it should be a stricter, "prove it" bar rather than something that's allowed to grow into over time, unlike some of the other pilot targets. Measured primarily via live pilot data (what reps actually do with real drafts), not just the pre-launch eval suite. Checked against 2026 industry data: no solid public benchmark exists specifically for assist-mode (human-reviewed) pilots — most published numbers are for fully autonomous resolution, which isn't an apples-to-apples comparison, so this number is reasoned from first principles rather than matched to a published target.
Changed my mind: also realized partway through that higher-risk categories (account access, money) might still get an AI-drafted response — just flagged for extra scrutiny — rather than skipping drafting entirely. Logged as open question 5.
Scope update (resolved via open question 5): decided to skip AI drafting entirely for money/security categories pending legal, so this Quality target currently applies only to categories that get a drafted response. For those skipped categories, the only thing measured is classification accuracy (correctly routing to a human), not draft quality. If legal later clears drafting for these categories, they need to be added back into this target's scope.

Human intervention — pilot target

Target: ≤ 20% of tickets require a substantive correction or override.
Tracked but not targeted: non-substantive (tone-only) edits — still surfaced, since a pattern there could point to a useful prompt/style tuning opportunity even though it's not a quality failure.
Reasoning: Defined as roughly the complement of the Quality target (80% clean approval ≈ 20% substantive correction) so the two numbers stay internally consistent rather than measuring the same thing from two different, conflicting angles.

Guardrails — pilot target

Target: Zero-tolerance, single-incident trigger for money/security-related categories — not a rate. Any one confirmed guardrail breach (wrong info or an attempted unauthorized action on refunds, credits, disputes, password resets, account changes, or security actions) immediately pauses autonomous drafting for that ticket category.
Response window: Within 24 hours of a confirmed breach — pause the affected category, notify the pilot owner (pending open question 6 on pause authority), and begin investigation.
Confirmation step: Suspected incidents get logged immediately, but only count toward the pause trigger once confirmed. With only 8 reps, I can personally follow up with the rep involved to verify what happened rather than relying on an automated flag alone.
Reasoning: Lower-stakes accuracy issues (e.g., a wrong answer on a basic how-to question) aren't guardrail breaches — those are covered by the Quality/Human intervention targets. Guardrails are reserved specifically for the human-boundary categories, where even one real failure (like the Trace Autopsy incident — outdated policy → incorrectly promised a 90% credit, two messages sent before detection) is too costly to wait on a rate threshold for.

Measurement — window and decision rules

Stabilization: Weeks 1-2 (training + initial use — not judged yet, since this is largely a routine workflow update rather than a new tool with a steep learning curve).
Measurement window: Weeks 3-8, with a built-in flexibility clause — if early Week 3 data looks off, reassess before treating it as final rather than reacting to noise.
Sources: Help desk tool data (timestamps, status), eval suite results, direct rep feedback/check-ins. Raw data requested directly rather than a pre-built dashboard (see open question 9).
Decision rules (Week 9+): Three real outcomes, not just pass/fail —
  • Continue/iterate — short of target but no guardrail breach; keep refining.
  • Expand to Tier 2 — targets hit; ready to grow scope.
  • Pause — guardrail breach; handled by the Guardrails rule above, not a wait-for-the-window decision.
VALIDATE checkpoint — eval designClassification, retrieval, failure diagnosis
Status: The v1 eval architecture is now defined around five areas: Ticket Classification, Knowledge Retrieval, Draft Response Quality, Appropriate Human Escalation, and Confidence & Review Routing. Classification and Retrieval are designed enough to show; the other three remain intentionally in progress. These cases are designed/planned, not yet presented as executed results.

Classification — discovery changed the expected behavior

Initial assumption: an ambiguous ticket should simply escalate.

What I learned: Meridian has an explicit Other / Needs Review category for issues that cannot be confidently assigned. Further discovery established two more rules: the customer's self-selected issue type is only a hint, and multi-issue tickets should be classified by the first blocking issue that must be resolved before the customer can proceed.
Changed my mind: “ambiguous = escalate” was too generic. The eval expectation should reflect the actual operating taxonomy and routing rules, not a rule I invented before asking how the workflow works.

Classification — safety cannot depend on one upstream label

Design insight: critical guardrails should not rely entirely on classification being correct. If a ticket requests an unauthorized financial action, the financial-action guardrail should still catch it even if the classifier assigns the wrong category. That keeps one classification error from expanding the blast radius into an unsafe action.

Retrieval — stale knowledge exposed a system dependency

Initial expectation: when current KB-101 and stale KB-107 both appear relevant to a monthly-report question, the agent should choose KB-101.

What challenged it: Meridian knows KB-107 is stale, but unless that freshness/authority information is actually available to the agent, the eval would be asking the model to know something the system never supplied.
Changed my mind: the fair v1 expectation is to avoid choosing arbitrarily and route the conflict for human review. The failure is partly a knowledge-system/design problem, not evidence that the model simply needs to be “smarter.”

Retrieval — score the failure so it can be diagnosed

Decision: use separate subscores for Source Selection, Safe Fallback, and Grounded Use, with N/A where a dimension does not apply. A case can therefore show Source Selection = Fail while Grounded Use = Pass — evidence that the model faithfully used the wrong retrieved source rather than hallucinating independently. That gives future trace analysis a more useful starting point than one opaque pass/fail result.

Offline evals are not production outcomes

The pre-launch suite can test controlled behavior such as classification, retrieval, escalation, grounding, draft quality, confidence, and review routing. Customer follow-up/reopen rates, successful closure, real rep edits, repeated customer pushback, and recurring corrections tied to the same KB article belong in production measurement. Those signals can later create new regression cases and identify KB-maintenance work.

Guardrail fix was only reverified against the cases that exposed it

The past-tense/imperative guardrail fix passed all four motivating cases after the regex change, but four cases is not the full 13-case suite. For a zero-tolerance guardrail, a false negative is worse than a false positive — narrowing the trigger to fix one false positive is exactly the kind of change that can quietly introduce a false negative elsewhere. Needs a full suite rerun before the fix counts as verified, not just "no longer reproduces the original bug."

The guardrail may need the opposite design bias from the metrics work

"Start dumb, prove the need for smart" fits quality measurement, where being wrong is cheap. It may be the wrong bias for the high-risk guardrail itself, which is deciding whether a ticket touching money or account security gets drafted at all. That component likely needs to favor recall — over-trigger, escalate more than strictly necessary — rather than the precision-leaning nudge today's fix made. Worth explicitly deciding which bias the guardrail should have, rather than defaulting to the same principle that governs the metrics layer.

Eval runs only exist in browser local storage

Local storage isn't a durable or versioned record — it's tied to one browser and disappears if storage is cleared. Given the pilot's whole pitch is proving readiness with data, the evidence itself needs a committed, checked-in record (a repo file, not just the Lab's local storage) before it can function as an actual audit trail.

Draft Quality, Escalation, and Confidence areas should consider organizing by failure mode, not feature area

Current practice increasingly organizes eval suites around failure-mode types — something like Facts, Scope, Tone/trust, Failure honesty, and Risk — rather than by feature area. Worth checking whether the eventual design for these three areas reflects that shape instead of reinventing a narrower one along old lines. Draft Quality's tone criteria (see Eval Work) already has real reasoning behind it; Escalation and Confidence are further behind and not yet backed by eval cases.

No prompt or context versioning alongside eval results

If classification or drafting logic is prompt-driven anywhere in the system, there's currently no way to compare which prompt version passed which eval cases. Without that link, a "fix" a month from now has no way of being checked against what came before it.

Confidence score calibration is unaddressed

Nothing yet checks whether an 80%-confidence draft is actually correct about 80% of the time. Since confidence is the gate for eventually unlocking selective auto-send, an uncalibrated confidence score undermines the entire premise of proving readiness with data — and it's a likely first question from an experienced reviewer.

The 5-exchange escalation threshold may be measuring the wrong thing

Exchange count is a proxy for "this conversation is going poorly," but it also fires on a customer with several separate, unrelated questions — a five-exchange thread covering five different topics isn't the same signal as five exchanges circling one unresolved issue. Same shape of problem as the guardrail's tense/intent conflation: a surface-level pattern standing in for the thing actually meant to be detected.

This isn't a new problem — the System Flow escalation design already lists an "upset/repeating customer" trigger alongside exchange count, so the design already assumes recurrence matters. What's still open is that this signal isn't specified precisely enough to implement, and none of the four described triggers exist in meridian-core.js yet. Topic recurrence across recent messages, checked against categories the classifier already assigns, looks like the closest path to a fixed-rule version of "repeating" — worth testing before treating it as settled.
ReflectionWhat I noticed about my own reasoning process
A shorter, measurement-specific reflection is in the Measurement Plan. This one's about the working process itself, across HANDOFF through CONFIGURE. The pattern I noticed most: my first answer to almost anything was usually close, but not quite precise — "reading the ticket" instead of "everything the agent can see," "drafting and sending" instead of "the decision about which path something takes." Getting from "close" to "actually right" took someone pushing back and asking me to distinguish it from something adjacent, not just re-explaining the same thing louder. I also noticed I do better reasoning when I have a concrete example to hang a concept on (Meridian) than when I'm working with the abstract idea alone — the "trigger/context/instructions/retrieval/routing/handoff/evals" framework only really clicked once I mapped each piece onto this specific pilot. That's probably useful to know about how I learn, going into a real role: ask for the concrete case, don't just take the definition at face value.

Where AI Earned Its Place in State

I initially approached State’s architecture by asking where AI would add value and what it might cost. Once I started testing the actual system, the more pressing questions were how long people had to wait, how reliably the model completed its work, and whether some tasks needed AI at all.

Those findings shaped three important decisions about State’s design.

Focus Model use, latency, reliability & cost
Decision 1 · AI or ordinary software

The authority boundary held. More of Ask moved into software.

From the beginning, I wanted software, not AI, to control project records and approvals. AI could interpret new information and suggest changes, but a person would decide what became official.

SoftwareRecords, approvals, which context Ask sees, reformatting
AIInterprets new information, suggests changes, writes answers
PeopleDecide what becomes official

As I built State, I found more work that didn’t need a model. Software could select the relevant project information before passing it to Ask, and simple requests to shorten or reformat an existing answer could be handled without another AI call.

That made the system more predictable and avoided unnecessary waiting and model costs.

Public demo: Automated tests cover the reformatting path, but the public demo answers each question fresh, so visitors don’t encounter it there.

Decision 2 · what latency measurements changed

I planned to model cost. Latency was what hurt.

I’d planned to measure State’s operating costs, but once I started testing it, speed became the more immediate problem. In one measured run, Ask took about 38 seconds to answer, with nearly all that time spent waiting for the model.

I explored faster models and reduced the amount of information sent with each request. A trial with a different model was even slower and failed State’s output checks, so I didn’t adopt it. The experience shifted my focus toward finding the right balance between speed, reliability, and cost.

Decision 3 · output allowance

A smaller output budget broke interpretation.

I also tried reducing how much the model could write in a single response to save time and cost. That worked against me when a complex project note required a more detailed interpretation. The model ran out of room, and the interpretation failed.

I restored the larger allowance. It was a useful reminder that reducing unnecessary AI usage is worthwhile, but not when it prevents the system from completing its job reliably.

Operating costs and safeguards

Not estimated yet

I didn’t want to estimate monthly AI costs without knowing how people would actually use State. The prototype doesn’t have enough representative production usage for a meaningful monthly cost figure yet.

Safeguard in place

Instead, I added a daily spending limit. If the AI budget is reached, features that need a model pause with an explanation, while the rest of State continues working.

What I learned

Building State changed how I think about using AI in a product. I learned to look beyond whether a model can perform a task and consider whether it needs to, how reliably it can do it, and what the user experiences while waiting.

Sometimes the better decision was to use ordinary software. Other times it was to give the model enough room to do its job well, even if that meant accepting a higher cost.

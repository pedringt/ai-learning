State architecture and cost: what I expected vs. what I learned

Before AI integration, I worked through how State should divide work between ordinary software and a model, what information the model actually needed, and how I would evaluate cost. Building the product changed which constraints mattered most.

Before Architecture and cost-planning exerciseAfter Working AI-integrated productFocus Complexity, model choice, latency & cost
Before I built it

I deliberately avoided pricing an architecture I hadn't chosen yet.

My pre-build approach started with the product problem, authority boundary, and information flow rather than choosing a model first. The plan was to keep State's authoritative mechanics deterministic, use a provider-neutral interface for interpretation, start with the smallest practical local stack, and compare providers on representative scenarios.

I also made an explicit decision not to invent precise public-demo limits or monthly AI costs before I had real usage data. The plan was to measure input tokens, output tokens, latency, and estimated cost per call first, then set guardrails from evidence.

The original ruleChoose the least-complex system that solves the problem well, then cost that architecture.
The initial architecture

AI was meant to interpret ambiguity, not own the product's rules.

Deterministic coreSoftware owns authority

Evidence persistence, validation, versions, Review lifecycle, Current State transitions, and history stay in software rather than being delegated to the model.

Model layerProvider-neutral interpretation

The application asks a model to interpret Evidence into structured recommendations. Provider adapters translate model-specific mechanics but do not get to define product behavior or mutate State.

ContextMinimum sufficient information

The early design intentionally avoided adding RAG by default. State's working context was small enough to use structured Current State, Rules, Reviews, and relevant Evidence directly.

StackStart simpler

SQLite was chosen for the learning build because it provided relational constraints and transactions without adding infrastructure before those concerns taught anything useful about State.

What the build changed

The expensive constraint was not the one I felt most.

Model choiceSmaller was good enough

The Anthropic path moved from a Sonnet default to Claude Haiku 4.5 as testing showed latency mattered and the smaller model could handle the bounded interpretation work. The model remained configurable rather than becoming an architectural dependency.

Output budgetMore tokens were not automatically better

Output limits were tightened as the product matured. Bounded structured responses and narrower context reduced unnecessary generation while keeping the deterministic application responsible for validation.

AskLatency became a product problem

Early Ask runs could take roughly 35–38 seconds, with instrumentation showing provider inference dominated the wait. The useful response was not simply “buy a stronger model.” I reduced context and output, tested alternatives, and eventually used true streaming so useful work appeared before the full answer completed.

ComplexityI kept resisting unnecessary AI infrastructure

State did not need an agent loop, vector database, or multi-agent system to prove its product thesis. The working product reinforced the original instinct to add AI capability only where flexible interpretation created value.

Before vs. after

The exercise became more useful once reality could challenge it.

BeforeMeasure model calls, tokens, latency, and cost before setting precise limits.

After: that restraint held up. The build produced real latency and model-behavior evidence instead of a polished but fictional monthly estimate.

BeforeKeep authoritative State transitions deterministic and use AI for interpretation.

After: this became even more important after valid model output still produced incorrect product meaning.

BeforeUse the lowest sufficient capability and avoid premature RAG or agent complexity.

After: the working product still did not need those layers for its core job.

BeforeCompare providers on quality, latency, tokens, and cost rather than familiarity.

After: model experiments reinforced that “different” or “stronger” did not automatically mean faster or better for State's workload.

What I would recommend now

Cost the workflow, not the idea of “using AI.”

If State became a real multi-user product, I would measure actual calls by workflow, context size, output size, retries, and active usage before forecasting spend. I would keep interpretation and Ask separately observable because their usage patterns and latency expectations differ, route work to the least-expensive model that clears the quality bar, and add caching or retrieval infrastructure only when measured usage shows a reason.

The bigger lesson from the exercise was that feasibility is not just a token-price question. Architecture determines how often a model is needed, what context it receives, how long a user waits, what can fail, and how much of the system remains predictable.

What I did vs. what AI did
My role

I worked through the product boundaries, challenged unnecessary complexity, decided what should remain deterministic, and used the build results to revise the original assumptions.

AI’s role

I used AI to help research implementation options, build the system, instrument and investigate performance, and pressure-test architecture choices. The recommendation and tradeoff decisions remained mine.

Where AI Earned Its Place in State

Before building State, I worked through where a model would add value, where ordinary software should stay in control, and what the tradeoffs would cost. I chose to measure real usage before estimating monthly cost rather than price an architecture I hadn’t chosen yet. Building it moved the question from what an LLM call costs to which parts of the workflow need a model at all, and showed that latency and reliability were the more immediate constraints. Three decisions show how.

Focus Model use, latency, reliability & cost
Decision 1 · AI or ordinary software

The authority boundary held. More of Ask moved into software.

Kept deterministic from the startRecords and authority

Evidence, Current State, Reviews, Questions, History, versions, and authority checks were always meant to live outside the model.

Moved into software during the buildContext and reformatting

State chooses and trims the records Ask receives before any model call. State also has a deterministic reformatting path. Given an existing answer and a request like “make this 3 bullets” or “shorten it,” it reshapes the answer with fixed rules and makes no new model call. Automated tests cover this behavior, but the public demo answers each question fresh, so visitors don’t encounter it there.

Used AI forInterpretation and synthesis

The model interprets new evidence and writes Ask responses from the context State prepares.

Adding AI made the deterministic parts more valuable, not less: every request software could handle on its own was one less model call to wait for.

Decision 2 · what latency measurements changed

I planned to model cost. Latency was what hurt.

The pre-build plan was to track calls, input and output tokens, model choice, retries, and non-model infrastructure, then stress-test low, base, and high usage. Once State existed, latency was the problem. I switched State’s default model from Claude Sonnet 4.6 to Claude Haiku 4.5 to cut provider latency. Even then, in one measured run of deployed State, Ask took about 38 seconds, about 36 of them waiting on the model. That moved the work to context, model, and interaction-design tradeoffs: Ask was narrowed to the records it needed, and many of the same fixes also cut token use and unnecessary calls.

I also tried GPT-4.1 mini on that Ask path. The one request took 48.9 seconds, needed two model calls and still failed State’s output checks, so Ask stayed on Haiku. It was a failed workflow test, not a model benchmark. Because the model sits behind an application interface, choices like these stay reversible instead of becoming product architecture: State has since moved to Claude Haiku 5.5 by changing the configured model behind that same interface.

Cost limitation: measuring before estimating was still the right call. State doesn’t have enough representative production usage to support an observed monthly operating cost, so this page doesn’t present one. What it does have is an operating limit: a daily cap on model spend. When the AI budget is used up, AI features pause with a plain explanation, and everything that doesn’t need a model keeps working.

Decision 3 · output allowance

A smaller output budget broke interpretation.

Lowering the interpretation output cap from 2,000 to 1,200 tokens looked like an easy cost and latency win. Then a prompt change made the model list every consequential point in a dense note instead of skipping some. In a stress test, one dense note ran out of room and the whole interpretation failed, so I decided to restore the 2,000-token allowance. The lesson was to cut waste, such as context the model doesn’t need, without cutting the room the model needs to finish a reliable interpretation.

Infrastructure: State runs on a FastAPI backend and SQLite, with the frontend deployed separately: enough real infrastructure to test the product thesis, not an enterprise architecture.

Architecture, cost, latency, and reliability turned out to be one product decision: which steps deserve a model call, what context each needs, how reliable it must be, and what the person experiences while it runs.

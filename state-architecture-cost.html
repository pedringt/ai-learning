Where AI Earned Its Place in State

Before building State, I worked through where a model would add value, where ordinary software should stay in control, and what the tradeoffs would cost. I chose to measure real usage before estimating monthly cost rather than price an architecture I hadn’t chosen yet. Building it moved the question from what an LLM call costs to which parts of the workflow need a model at all, and showed that latency and reliability were the more immediate constraints. Three decisions show how.

Decision 1 · AI or ordinary software

More of State stayed deterministic than I first expected.

Kept deterministicRecords, authority, and context selection

Evidence, Current State, Reviews, Questions, History, versions, and authority checks live outside the model, and State chooses the bounded context Ask receives.

Used AI forInterpretation and synthesis

The model interprets new evidence and writes Ask responses from the context State prepares.

Deterministic rules became more important after AI was added, not less.

Decision 2 · what latency measurements changed

I planned to model cost. Latency was what hurt.

The pre-build plan was to track calls, input and output tokens, model choice, retries, and non-model infrastructure, then stress-test low, base, and high usage. Once State existed, an early Ask could take roughly 35–38 seconds, and instrumentation showed provider inference dominated the request. That moved the work to context, model, and interaction-design tradeoffs: Ask was narrowed to the records it needed, and many of the same fixes also cut token use and unnecessary calls.

At the time, State ran Ask on Claude Haiku 4.5. A GPT-4.1 mini experiment was slower on that Ask path in the workflow I measured, so Haiku stayed. The model sits behind an application interface, so a choice like that stays reversible instead of becoming product architecture.

Cost limitation: measuring before estimating was still the right call. State doesn’t have enough representative production usage to support an observed monthly operating cost, so this page doesn’t present one.

Decision 3 · output allowance

A smaller output budget broke interpretation.

Lowering the interpretation output cap looked like an easy cost and latency win. Dense notes then started truncating and failing, so I decided to raise the output allowance again. The lesson was to cut waste, such as context the model doesn’t need, without cutting the room the model needs to finish a reliable interpretation.

Infrastructure at the time: State started with a FastAPI backend and SQLite, with the frontend deployed separately: enough real infrastructure to test the product thesis, not an enterprise architecture.

Architecture, cost, latency, and reliability turned out to be one product decision: which steps deserve a model call, what context each needs, how reliable it must be, and what the person experiences while it runs.

Research & Methods Deep Dive

The full reasoning record: hypothesis, fixture, AI-assisted experimental design, repeated runs, failure analysis, research, product decisions, objections, limitations, and next tests.

This project started with a question about something I'd mostly been calling context: software teams work from messy histories, tickets, notes, decisions, evidence, things proposed but never approved, and I wondered what happens when AI starts doing more of the work of turning that history into answers.

I'd been running into a specific version of this myself: my own Claude and ChatGPT conversations would occasionally make things up, or ask me things I'd already told them. That's what sent me looking.

01

Before there was a formal test

Before any formal test, I caught AI turning an observation into an unearned decision: a rep mentioning that they search Slack became “Slack is a proposed knowledge source.” That gap between evidence and accepted state became the thread I followed.

02

AI turned that into a testable hypothesis

AI framed what I'd noticed into a testable hypothesis: that AI struggles to reliably reconstruct a team's current understanding from fragmented history, and an explicitly maintained version would work better. I ran every test condition myself before anything was built.

03

What AI's analysis of the results taught me

The results didn't cleanly validate the idea, which made it more interesting. Strong models reconstructed current state better than expected, and a stronger prompt improved that further, but a smaller failure kept appearing: the model could understand the project well and still make an unresolved answer more definite than the evidence supported.

That distinction changed what I researched, what got built, and what I now think the interesting design question actually is.

01What happens when AI has to decide what is still true?+

The original idea came from thinking about how project context actually works in software teams.

A project record is not a clean database of current truth. It contains different kinds of things:

  • decisions that still apply;
  • decisions that were later changed;
  • stakeholder observations;
  • proposals that were never approved;
  • unresolved questions;
  • assumptions people are operating on;
  • evidence that weakens an assumption without supplying a replacement;
  • rationale that explains why a decision made sense at the time.

People do not treat all of those as interchangeable. In practice, teams reconcile them while doing the work.

That made me wonder whether I had been thinking about AI context too narrowly.

The question was not only:

Can the model find the relevant information?

It was also:

Once it finds that information, how does it decide what the implementation should rely on now?

My initial answer was that the system might need an explicitly maintained representation of current understanding rather than asking a model to reconstruct it from history every time.

That was still only a hypothesis.

So before turning it into a product claim, I wanted to see whether the underlying behavior was actually observable.

02A fixture where "current" was not the same as "latest"+

AI built a synthetic AI Support Pilot scenario, at my direction, with enough history to create realistic ambiguity without making the experiment impossible to inspect.

The fixture included:

  • current implementation decisions;
  • earlier assumptions;
  • later evidence;
  • stakeholder statements;
  • leadership requests;
  • proposed ideas;
  • unresolved questions;
  • decisions with rationale;
  • information that was relevant but not authoritative.

One scenario became especially important.

The feature-access assumption

The implementation had been operating on an assumption that standard plan rules were sufficient to determine customer plan and feature access.

Later, a Senior Support Rep provided new evidence:

  • temporary feature access exists;
  • grandfathered accounts exist;
  • account-level exceptions therefore mean standard plan rules are not always sufficient.

That evidence weakened the old assumption.

But it did not establish the replacement answer.

The team still had not established which source should be treated as authoritative for a customer's effective access.

So the real state transition was:

Previously
Standard plan rules are sufficient.

New evidence
Temporary and grandfathered access create exceptions.

What changed
Standard plan rules alone are no longer safe to treat as sufficient.

What remains unresolved
Which source should determine effective customer access.

That middle state mattered to me because it is easy to flatten:

The old answer is no longer safe, but the new answer is not established yet.

I also included other distinctions that could expose overreach. A leadership request for 50% autonomous resolution was not an implementation commitment. Observations about predictable troubleshooting cases did not establish a safe automation percentage. A source someone used operationally was not automatically an authoritative source of truth.

The six frozen questions

I tested every condition with the same six questions:

  1. Prepare for the upcoming Security meeting, including current direction, recent changes, boundaries not to blur, unresolved questions, and what Security is best positioned to answer.
  2. What percentage of troubleshooting tickets can we safely automate now?
  3. Why aren't we just automating the predictable troubleshooting cases first?
  4. What's the status of the 50% autonomous-resolution target?
  5. What source should the AI use to determine a customer's plan and feature access?
  6. What assumption about plan and feature access changed, and why?

I asked the questions individually and did not correct the model between them.

The scoring rubric

Using a rubric AI built, responses were scored across five dimensions:

Dimension Maximum State fidelity 4 Uncertainty preservation 3 Idea/proposal containment 3 History/authority discipline 3 Downstream usefulness 2 Total 15

The rubric mattered because a response could sound useful while quietly changing the project's state.

A particularly important high-severity failure was converting an unresolved state into a definite operational fact or metric.

03Archive reconstruction vs. maintained understanding+
AProject historyReconstruct current state from archive
BMaintained understandingCurrent state explicitly organized
CHistory + strong instructionsStrengthened reconstruction approach

My first comparison had two conditions.

Condition A --- Project history

The model received the accumulated project archive: history, stakeholder statements, evidence, decisions, proposals, and unresolved questions.

It had to reconstruct the current implementation understanding from that material.

Condition B --- Maintained understanding

The model received the same substantive information organized so that current decisions, supporting evidence, relevant history, investigations, and unresolved questions were explicitly separated.

That reduced how much status reconstruction the model had to perform at answer time.

My expectation was straightforward:

Condition B would perform noticeably better because the model would not have to reconstruct current state from the archive.

It did perform somewhat better.

But the difference was smaller than the theory in my head had led me to expect.

More importantly, Claude was often quite good at reconstructing the project from history.

It generally understood the central feature-access transition correctly: the old plan-rule assumption had been weakened, and the replacement source remained unresolved.

That was important negative evidence.

If the model could recover that transition from history, I could not keep telling the story as:

AI cannot reliably determine what is current unless the system maintains it explicitly.

The experiment was already pushing me toward a narrower claim.

04Maybe I had just made one condition easier+

After the first comparison, AI flagged an obvious weakness in the experiment, and I agreed it needed to be addressed rather than protecting the result I already had.

Condition B had been given a cleaner representation of the project. Condition A had been asked to reconstruct that representation from history.

If B performed better, maybe the mechanism was not the interesting part.

Maybe I had simply given B an easier job.

So the testing approach added a third condition specifically to strengthen the competing explanation.

Condition C --- Project history + strong reconstruction instructions

Condition C received the same underlying archive as Condition A, but with much stronger instructions to reconstruct the current state carefully before answering.

The prompt explicitly told the model to distinguish:

  • current decisions and boundaries;
  • stakeholder reports;
  • historical or superseded understanding;
  • proposed ideas;
  • unresolved questions;
  • model inference.

It also told the model to preserve unresolved states, avoid turning observations into requirements or metrics, avoid resurrecting superseded assumptions, and recognize when evidence weakens an old assumption without establishing a replacement.

This was not an attempt to make Condition C fail.

It was the opposite.

If better prompting could recover the same behavior as maintained understanding, I wanted the experiment to show that.

Why this changed the project

Condition C did substantially better than a simplistic version of my original theory would predict.

It reconstructed current state well.

Its overall score was slightly higher than the ordinary archive condition.

That meant I had to preserve a less convenient conclusion:

Strong models can often reconstruct current project understanding from history, especially when the task is framed carefully.

That weakened the broad hypothesis.

It also made the remaining differences more useful, because I could stop treating every archive mistake as evidence for maintained state.

05The average scores were close+

Claude provided the cleaner primary comparison.

Condition Run 1 Run 2 Run 3 Average High-severity failures A --- Project 13 14 13 **13.3 / **2 / 3 history** 15**

B --- Maintained 14 14 14 **14.0 / **0 / 3 understanding** 15**

C --- Strong 13 14 14 **13.7 / **2 / 3 reconstruction** 15**

The difference in average score is small.

I do not treat it as evidence that maintained understanding is generally superior.

In fact, several questions showed little meaningful difference between conditions.

What all three conditions generally got right

The central feature-access transition was handled well across conditions.

The models generally recognized:

  • plan rules had previously been treated as sufficient;
  • new evidence showed account-level exceptions;
  • the old assumption therefore had to weaken;
  • the evidence did not establish a replacement authoritative source.

That matters because this was one of the most consequential state changes in the fixture.

If all three conditions could usually reconstruct it, the experiment could not support the broad claim I started with.

What Condition C established

Condition C also answered an important objection:

Maybe the archive only looked worse because the model needed stronger reconstruction instructions.

There is truth in that objection.

Stronger prompting improved reconstruction and produced generally strong answers.

But it did not eliminate every consequential failure.

That is where the diagnostic automation question became more interesting than the aggregate score.

06The failure I followed+

One question produced the clearest repeated difference:

What percentage of troubleshooting tickets can we safely automate now?

The supported project state was:

Unknown. No safe percentage has been established.

It was not:

0%.

Those answers can sound close in ordinary conversation, but operationally they mean different things.

Unknown means the evidence is insufficient to determine the answer.

0% means the answer has been determined and the determined value is zero.

Claude produced:

Condition Run 1 Run 2 Run 3 A --- Project ❌ none / 0 ✅ unknown ❌ none / 0 history

B --- Maintained ✅ unknown ✅ unknown ✅ unknown understanding

C --- Strong ❌ none / 0 ✅ unknown ❌ none / 0 reconstruction

So uncertainty was preserved:

  • Project history: 1 / 3
  • Maintained understanding: 3 / 3
  • Strong reconstruction: 1 / 3

This was the finding I kept coming back to.

The model was not wildly hallucinating.

It was making a plausible interpretation that was slightly more definite than the evidence allowed.

That felt much closer to the kind of AI failure I would worry about in project work.

A dramatic nonsense answer is easy to reject.

A reasonable answer that quietly changes "we don't know yet" into "we know the answer is zero" is harder to notice.

Plausible completion showed up elsewhere too

The same pattern appeared in smaller ways.

Across archive/reconstruction responses, Claude occasionally supplied reasonable but unsupported connective reasoning, such as:

  • assigning responsibilities to Security that the archive had not explicitly assigned;
  • inferring stakeholder ownership;
  • explaining why the team made a decision when only the decision itself was documented;
  • describing evidence as "ground truth";
  • treating an accepted understanding as a "binding fact";
  • inferring authority from the existence or use of a source.

Most of those did not ruin the final answer.

That was part of the point.

The failure mode was often plausible completion, not obvious fabrication.

Source does not automatically mean authority

One example sharpened another distinction.

The archive established that a Senior Support Rep used an admin tool to inspect customer plan and enabled features.

In one response, Claude inferred that there was therefore "a source of truth."

But the project state explicitly preserved a different conclusion:

The authoritative source for effective customer access remained unresolved.

Knowing that a source exists---or that someone uses it---is not the same as knowing that the team has authorized that source to determine operational truth.

Again, the model often recovered to the right final conclusion.

The interesting part was how many interpretive steps reconstruction invited along the way.

07I did not want to build a product theory around one weird answer+

At this point, I had a small experiment and an interesting failure.

That was not enough to conclude that I had found a new AI architecture problem.

So I researched the surrounding ideas and tried to separate concepts I had previously been grouping together as "context."

Finding information and deciding what it means now are different problems

Retrieval answers a question like:

What information is relevant to this task?

But a model can retrieve the right history and still have to decide:

  • which statement is current;
  • whether a later statement superseded an earlier one;
  • whether something was a proposal or a decision;
  • whether a source is merely informative or actually authoritative;
  • whether the project has an answer or is still unresolved.

That led me to a more useful distinction:

History is what has been said.

Retrieval is what information is relevant.

Synthesis is what the model thinks that information means now.

Maintained state is an explicit representation of what the system is currently allowed to operate on downstream.

The experiment does not prove the fourth layer is necessary.

It gave me a reason to investigate when explicitly representing some of those distinctions might be worth the maintenance cost.

Uncertainty is not always missing context

The automation example also changed how I thought about "missing information."

Sometimes the correct state is not a fact waiting to be retrieved.

Sometimes the current state is:

We have not established this yet.

In that situation, uncertainty is itself information.

Omitting it---or allowing it to collapse into a plausible default---changes what the organization knows.

New evidence does not always produce a new answer

The feature-access example made another distinction concrete.

New evidence can tell you that the old assumption is no longer safe without telling you what should replace it.

That means a useful state model may need to preserve transitions like:

OLD = no longer safe → NEW = not yet established → downstream = qualify / pause / verify

That is different from a simple old-value/new-value update.

These ideas are not novel

Research also made it clear that pieces of this problem already exist in adjacent disciplines and products.

Requirements and change-management practice already deals with baselines, rationale, assumptions, review, approval, traceability, and version history.

Knowledge systems already represent relationships and organizational context.

AI systems already use retrieval, citations, memory, structured context, and human review.

So I stopped asking whether I had discovered a new category.

The more useful question became:

What does this combination of ideas look like when AI is continuously interpreting messy implementation evidence and producing downstream work from it?

That is a much smaller claim, and a more productive design question.

Once the broad hypothesis weakened, I did not want the prototype to keep pretending it had been validated.

I narrowed it.

The review and state-update architecture described in this section, how new evidence stays separate from what the project currently treats as true, when a change needs review, how pending evidence shows up again where it matters, was primarily designed by AI, interpreting what the experiment implied. I questioned and refined that design and focused most of my direct contribution on the UI around it.

The working question became:

What should an AI-supported system do when new information challenges something the implementation is already relying on?

That led to a few specific product decisions.

Decision 1 --- "Not established" is a valid answer

If the implementation has not established a safe automation percentage, the system should not have to manufacture a useful-sounding number.

In the prototype, Not established is a legitimate answer.

The goal is not to make the AI less useful.

It is to make the boundary visible so the user can decide what evidence is needed next.

Decision 2 --- Evidence does not automatically become accepted state

The prototype separates incoming evidence from what the implementation currently operates on.

For the feature-access scenario, Review shows:

Currently operating on
Plan tier reliably determines feature access.

New evidence
Temporary access and grandfathered accounts create account-level exceptions.

What the evidence establishes
Standard plan rules alone are not always sufficient.

What it does not establish
Which source should determine effective access.

The user can update the current understanding or keep the existing understanding.

Either way, the evidence remains in history.

That prevents a common simplification:

new evidence → automatic replacement truth

Sometimes the right update is only:

the old assumption is weaker than we thought.

Decision 3 --- Human review belongs at consequential state transitions

I became less interested in generic "human in the loop" language.

The reason for review in this prototype is specific:

The system is proposing a consequential change to something downstream AI will rely on.

Low-consequence supporting detail does not need the same friction.

A potential state change does.

An unresolved question remains unresolved.

A speculative idea stays an investigation rather than silently becoming a plan.

Decision 4 --- Review cannot depend on perfect queue hygiene

My first instinct was to make Review a queue.

Then I thought about how people actually work.

A queue only protects downstream work if somebody remembers to clean it up.

So the prototype keeps the Review queue, but relevant pending evidence can also resurface during normal work.

For example, Meeting Prep can say:

1 pending review may affect this briefing.

The user can review it now or continue with the currently accepted state.

The pending evidence does not silently become truth.

But the system also does not pretend the evidence does not exist.

That led to one of the product principles I care most about from the project:

The system shouldn't depend on perfect knowledge-management habits to keep important project understanding current.

Decision 5 --- Keep the prototype deterministic where that is enough

I did not add embeddings, a generic semantic-retrieval layer, or an LLM pipeline just to make the prototype look more sophisticated.

The current prototype uses controlled fixtures and deterministic behavior.

That means it does not demonstrate that arbitrary real-world evidence can be interpreted correctly.

That is a limitation.

It is also intentional scope control.

The thing I wanted to test at this stage was the interaction and state model:

  • how evidence enters;
  • how a consequential change is reviewed;
  • how uncertainty survives;
  • how accepted state changes;
  • how downstream work behaves before and after that change.

Adding more AI machinery would have made the demo more impressive-looking without necessarily making that question easier to answer.

09The useful path mattered more than the Review page+

Once the core state transitions worked, I tested the prototype less like its designer and more like someone trying to get work done.

That changed the emphasis.

The most likely useful actions were not:

"I should go maintain my project knowledge system."

They were:

  • answer a question;
  • prepare for a meeting;
  • catch up on what changed;
  • add something I just learned.

That led to a Useful → Interesting → Sophisticated product arc.

Useful

The primary experience became normal implementation work:

  • Ask this implementation
  • Prepare for a meeting
  • Catch me up / status update
  • Add project update
  • See current open questions

Interesting

The system's behavior reveals the underlying idea without requiring the user to understand the experiment first:

  • Not established instead of invented 0%;
  • a leadership request remains a request, not a commitment;
  • pending evidence can affect an answer without silently changing accepted state;
  • the authoritative feature-access source remains unresolved.

Sophisticated

Review and History explain why:

  • evidence is not automatically accepted state;
  • an assumption can weaken without a replacement;
  • pending is different from accepted;
  • reviewed-but-kept evidence remains in history;
  • unresolved questions constrain downstream answers.

This also changed how I treated contextual review.

I did not add warnings everywhere.

Ask and Meeting Prep became the main places where relevant pending evidence resurfaces because that is where it could actually affect the work.

QA became part of the AI-product thinking

My QA background was useful here in a way I had not fully appreciated at the beginning of the project.

The interesting failures were often not broken buttons or obviously wrong answers.

They were state-integrity failures:

  • does a rejected idea accidentally return as current?
  • does "unknown" become zero?
  • does a leadership target become an implementation commitment?
  • does pending evidence silently alter downstream output?
  • does resolving one question accidentally resolve another?
  • does history remain distinct from current understanding?

I also tested ordinary UX failure paths: modal behavior, scroll position, mobile layout, navigation, focus, and state persistence.

But the more important lesson was that AI QA often requires checking whether a perfectly reasonable-looking output has crossed a boundary the evidence did not support.

The happy path is not always where the interesting failure lives.

10Why not just use Claude with project history?+

This is the strongest objection, and my own experiment supports part of it.

A strong model with good instructions can often reconstruct current project understanding surprisingly well.

Condition C was included to give that approach a fairer test.

So I would not claim that teams need a separate maintained-state system because models cannot reconstruct current state.

They can.

The narrower question is:

Are there some consequential distinctions---unknown, unresolved, superseded, not approved---that we care enough about that downstream AI should not have to reconstruct them correctly every single time?

My experiment gives me a reason to keep investigating that question.

It does not answer it.

Why not retrieval or RAG?

Retrieval could help the model find the right evidence.

That is useful, but it does not automatically answer the status question.

A retrieved passage can still be:

  • historical;
  • superseded;
  • a proposal;
  • a stakeholder opinion;
  • unresolved;
  • relevant but not authoritative.

A good retrieval system plus strong synthesis may handle those distinctions well enough.

That is one of the alternatives I would want to test next.

The project does not establish that maintained state is better than RAG or retrieval.

Why not just keep this in Markdown or Notion?

This deserves a real answer, not a dismissal.

Structured documentation---a well-run Notion page, a decisions doc, an "Open Questions" section someone actually maintains---can already represent assertions, statuses, decisions, evidence, and superseded information.

So State's value cannot simply be that it stores this information. People can already write "UNRESOLVED---do not infer a resolution" in a Google Doc.

The real comparison is not storage format. It's maintenance effort:

Does a lightweight maintenance workflow reduce enough of the effort of keeping explicit project state current to justify dedicated tooling, compared with maintaining the equivalent structured document by hand?

I don't know the answer yet. It's the open question the rest of this chapter tries to be honest about.

Maintained state can fail too

This is the most important counter-risk.

Maintained state does not eliminate the state problem. It relocates it.

An explicit current-state layer can become:

  • stale;
  • wrong;
  • falsely authoritative;
  • oversimplified;
  • burdensome to maintain;
  • disconnected from source systems;
  • a competing source of truth;
  • too clean to preserve legitimate disagreement or nuance.

If a system gives maintained state privileged downstream influence, errors in that layer could become more consequential, not less.

That is why the prototype keeps history, source information, unresolved questions, and human review around consequential changes.

But the prototype does not prove that those safeguards are sufficient.

The experiment was small and synthetic

AI designed the fixture, at my direction and with my review.

That gave me control, but it also means the scenario may favor the distinctions I was interested in.

The experiment used a small number of questions and repeated runs, not a benchmark large enough for statistical claims.

The scoring rubric involved judgment.

Model behavior can change over time.

The maintained condition also had a representational advantage: important distinctions were explicitly organized for the model.

That is partly the mechanism being explored, but it means the comparison is not a neutral test of two equally structured inputs.

ChatGPT was not clean independent evidence

ChatGPT scored effectively perfectly across conditions.

I do not use those results as the primary comparison.

During testing, a contamination risk surfaced: fresh ChatGPT conversations could have access to cross-conversation/user context about the project.

That meant I could not confidently establish that the answers relied only on the experimental fixture.

I retained those runs as supplementary observations and used Claude as the cleaner comparison.

That was frustrating, but hiding the contamination would have made the experiment look cleaner than it actually was.

I have not validated the product with real implementation teams

The prototype demonstrates the interaction model in a controlled scenario.

It does not establish:

  • that teams experience this problem frequently enough to justify a product;
  • that maintained state would improve real implementation outcomes;
  • that users would keep the state accurate;
  • that the review burden would be acceptable;
  • that this should be a standalone product rather than a capability inside an existing implementation, PM, CRM, or knowledge tool.

I am deliberately leaving those questions open.

Where would the initial state come from?

The prototype starts mid-project, already populated. A real version has to start somewhere, and none of the honest options are free.

If AI reconstructs the initial state from existing history, the reconstruction problem this whole project is about comes right back, just once instead of every time. If a person builds it by hand, that's real setup cost before the tool has proven any value. If state only starts being trustworthy from the moment maintenance begins, then a project already six months in only gets partial protection, and it may not be obvious to a new user which parts of the record they can rely on and which are still catching up.

I don't have a solved answer here. I'd rather say that plainly than build a fake onboarding flow that quietly assumes the problem away.

Whose state, if more than one person is involved?

"Here's what the project currently believes" is useful language, right up until different parts of an organization believe different things at the same time and are each right from where they sit: engineering believes one thing, sales has promised another, legal requires a third, product decided a fourth. Those aren't obviously just conflicting scraps waiting to collapse into one canonical answer.

The prototype stays single-user on purpose. One reviewer working with evidence generated by many people and sources is enough to demonstrate the review-and-state-change interaction. It is not enough to show that one maintained project state can represent what a whole organization actually believes, and I'm not claiming it does. Team governance is out of scope here, not solved off-screen.

The current bet, and what would kill it

I'm not going to end this on an A/B/C shrug. Here is where I actually land, and what would move me off it.

B, the current hypothesis: a lightweight maintenance workflow for explicit, portable project state is worth testing further.

C, the strongest competing explanation: disciplined structured documentation may already provide enough of the value that dedicated software isn't warranted.

I currently believe B is worth testing next. I have not established that B beats C. That's the bet, not a conclusion.

I'd move toward C if a State-style maintenance workflow doesn't meaningfully reduce the effort of keeping the record current compared with maintaining the equivalent structured document manually---or if people, given the choice, simply prefer editing the document directly.

Laid out plainly, here's what would actually kill this idea, not just dent it:

  • Manual structured notes turn out to be sufficient. If disciplined documentation gets teams comparable value without another workflow to maintain, State doesn't need to exist.
  • Maintenance costs more than it saves. The tradeoff cuts both ways: surface too much and review becomes another chore; surface too little and people develop false confidence in an incomplete record---quietly assuming "if something contradicted this, State would have flagged it." An imperfect State could leave people more confident in incomplete understanding than messy documentation ever would have. That's a genuinely product-killing failure mode, not a small UX gap.
  • Consequential changes can't be surfaced reliably enough. This prototype preconfigures which incoming evidence deserves review. A real version needs that judged automatically, and the two ways to get it wrong---too many irrelevant reviews, too many missed changes---pull against each other.
  • Users don't actually trust the maintained record. If people keep independently reconstructing history before relying on State anyway, the workflow hasn't reduced the problem it was built to reduce.
  • The underlying pain isn't important enough. Teams may already manage this adequately through ordinary project practice, and this never rises above a nice-to-have.

Any one of those is a real reason to stop, not a reason to add another feature and try again.

11What I would test next+

The next useful work is not adding more features.

It is trying to falsify the narrower idea under more realistic conditions.

1. Broader reconstruction tests

Use larger, messier project histories with more:

  • superseded decisions;
  • conflicting stakeholders;
  • unresolved questions;
  • partial replacements;
  • ambiguous authority;
  • longer time spans.

Then compare whether retrieval + synthesis preserves those distinctions as reliably as an explicit maintained representation.

2. Real downstream tasks

Test more than direct questions.

For example:

  • meeting preparation;
  • implementation plans;
  • status updates;
  • troubleshooting guidance;
  • risk summaries;
  • requirements drafts.

The question is not only whether the model can state the current truth when asked directly.

It is whether the distinction survives when it is only one dependency inside a larger task.

3. Maintenance failure

Deliberately make maintained state stale or wrong.

Then test whether traceability and review mechanisms help users detect the problem---or whether the explicit state simply becomes a more convincing source of error.

4. Human behavior

Put the workflow in front of real implementation or project practitioners.

I would want to know:

  • Do the distinctions make sense without explanation?
  • Which changes actually deserve review?
  • Does contextual resurfacing help or annoy?
  • Would people maintain this?
  • Which information already has an authoritative system of record?
  • Where does the workflow duplicate existing work?

What would change my mind?

I would become less confident that explicit maintained state is useful if retrieval + strong synthesis reliably preserves unresolved, superseded, and authority-sensitive distinctions across broader realistic projects and downstream tasks.

I would become more confident if those distinctions repeatedly degrade during reconstruction---and explicit representation improves downstream behavior enough to justify the maintenance cost and new failure modes it introduces.

That is the standard I would use now.

12What I learned+

I started this project knowing the basic vocabulary around context windows, RAG, prompting, human review, and evaluation.

Building and testing something forced me to understand where those ideas stop being interchangeable.

I learned that finding the right information and deciding what the project currently permits the system to conclude are not necessarily the same task.

I learned that uncertainty can be part of the current state rather than a hole waiting to be filled.

I learned that new evidence can weaken an old assumption without earning a replacement.

I learned that a plausible answer can be more dangerous to an evaluation than an obviously bad one, because the mistake may be a small unsupported step rather than a dramatic hallucination.

I also got practice doing something I want to keep getting better at: turning a fuzzy AI question into something testable, recognizing a sound methodological challenge and letting it into the experiment instead of protecting my original idea, looking closely at failure behavior instead of only aggregate scores, and changing the product when the evidence did not support my first explanation.

I did not come out of the project thinking I had discovered a new category of AI architecture.

I came out of it asking a narrower question:

AI can often reconstruct current project understanding from history. But when distinctions like "unknown," "superseded," or "not established" constrain what happens next, repeatedly reconstructing those distinctions may not always be the right system design.

That's a much narrower conclusion than the one I started with.

Experiment detailsFixture, conditions, frozen questions, rubric, full compact results, and claims the experiment does not support+

Research question

When project evidence changes over time, does explicitly maintaining current implementation understanding help an AI preserve consequential distinctions---particularly status, authority, and unresolved uncertainty---more consistently than reconstructing that understanding from project history?

This experiment does not attempt to establish that maintained state is generally superior to retrieval, long-context prompting, RAG, or other context-management architectures.

Conditions

A --- Project archive/history

The model received project history containing stakeholder statements, evidence, decisions, proposals, and unresolved questions and had to reconstruct current understanding.

B --- Maintained current understanding

The model received an explicitly maintained representation distinguishing current decisions and boundaries, supporting evidence, investigations, relevant history, and unresolved questions.

C --- Archive + strong reconstruction instructions

The model received the same archive as A plus explicit instructions to reconstruct current state carefully, including status, authority, supersession, unresolved questions, and unsupported inference.

Frozen questions

  1. Prepare for the upcoming Security meeting, including current direction, recent changes, boundaries not to blur, unresolved questions, and what Security is best positioned to answer.
  2. What percentage of troubleshooting tickets can we safely automate now?
  3. Why aren't we just automating the predictable troubleshooting cases first?
  4. What's the status of the 50% autonomous-resolution target?
  5. What source should the AI use to determine a customer's plan and feature access?
  6. What assumption about plan and feature access changed, and why?

Supported interpretation

In this small exploratory comparison, Claude could usually reconstruct current implementation understanding from project history, particularly when given explicit reconstruction instructions. However, explicitly maintained current understanding more consistently preserved one consequential unresolved state: whether any percentage of troubleshooting was currently safe to automate.

Both the ordinary archive condition and the strong-reconstruction condition converted "unknown" into "none/0%" in two of three runs. The maintained-current-understanding condition preserved the unresolved state in all three.

This is evidence worth further exploration, not a general proof.

Claims this experiment does not support

Do not claim that the experiment proves:

  • maintained state is superior to retrieval;
  • maintained state is superior to RAG;
  • models cannot reconstruct current state from history;
  • maintained state eliminates hallucination;
  • maintained state prevents context drift;
  • maintained state is necessary for reliable AI systems;
  • the approach generalizes across models, domains, or workflows;
  • the observed differences are statistically significant;
  • maintained state was better on every tested question.

Building State with AI

I built State to test whether a project’s current understanding could be maintained explicitly instead of reconstructed from history every time. I also wanted to see what changed when AI was both part of the product and a development collaborator.

The product forced concrete decisions about AI authority, deterministic controls, retrieval, review burden, latency and information design. Several of my first answers were wrong; using the product is what exposed them.

The problem

I wanted to know whether “what is true now” could be maintained instead of reconstructed.

As my AI projects got longer, I kept summarizing one chat, carrying that context into the next, and eventually doing it again. The handoff worked, but project history still left a harder question: which information actually governs now?

I tested the premise before overbuilding. A maintained summary scored 14.0/15 against 13.7/15 for stronger reconstruction instructions and 13.3/15 for raw history. The gap was too small to claim a win, but one failure was more interesting than the scores: AI repeatedly turned an unresolved automation target into a confident 0%. “Unknown” had quietly become “none.”

What I built

I made authority explicit before I added model uncertainty.

The first State prototype was deterministic: preserve submitted Evidence, keep it separate from Current State, require Review for consequential changes, and prevent stale decisions from overwriting newer ones. Then I gave the model one bounded job: interpret messy updates and recommend what they might mean.

New information→AI interprets→Software validates→Human decides→State changes

The boundary: the model can interpret and recommend; deterministic software enforces references, versions and constraints; a person authorizes consequential changes.

What AI changed

Structured output was not the same as trustworthy behavior.

Valid output could still be wrong.

A response could match the schema and still reference the wrong thing or propose a stale/no-op change. Those checks stayed in software.

AI failure could not become data loss.

State saves Evidence before analysis, so a provider failure can retry against the same information instead of asking the user to submit again.

“No change” had to be legitimate.

Useful Evidence does not always deserve another maintained fact. Repeated information can support what is known without creating unnecessary Review work.

Using it changed the product

Several of my first answers were wrong.

RetrievalI blamed the model for a bad billing-contact answer.

The actual failure was frontend routing. I moved fresh factual questions onto grounded backend retrieval with deterministic handling for direct facts.

Information designI made Project too much like a database viewer.

Technically distinct facts became hard to distinguish. I kept atomic State underneath but redesigned Project as a readable maintained wiki.

LatencyI shipped an Ask experience that waited roughly 35–38 seconds.

Instrumentation showed model inference dominated the delay. I tested alternatives, simplified the path and used real streaming instead of faking progress.

How the build was divided

I directed the product; AI contributed substantially to implementation.

My role

Product concept, requirements, UX direction, evaluation, acceptance criteria, tradeoffs, hands-on use and final decisions about what was worth changing.

AI’s role

Technical approaches, much of the frontend/backend implementation, model integration, debugging, log analysis and automated QA.

Where I landed

State earns its maintenance only when “what is true now” needs explicit authority.

The maintained view became genuinely easier to rely on once the project accumulated decisions, contradictory updates and unresolved questions. Reviews, provenance and History mattered when I cared about how a change became authoritative, rather than settling for a plausible summary reconstructed by a model.

I would not use State for every project. For a lightweight solo project, a maintained Claude Artifact or similar document is probably easier and good enough. State becomes more useful when consequential changes need review, current understanding needs explicit ownership, or several people need to distinguish new Evidence from accepted project truth.

I built the deterministic prototype quickly, then spent about three focused days turning it into the AI-integrated product I could use, break and refine. At that cost, building became part of the research.

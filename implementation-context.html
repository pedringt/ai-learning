Building State with AI

I built State to explore a harder product question: what should AI be allowed to interpret, and what should still require human authority? The result is a system for keeping project understanding current without letting model output change Current State unless a person authorizes it.

My role Product framing, UX direction, evaluation & QAAI collaborator Product, design, engineering & QA supportStatus Working product · portfolio build

In shortState keeps the AI’s reading of project evidence separate from what a person has approved as current, so a confident guess cannot become Current State until a person authorizes it.

In plain language:

A team lead adds meeting notes, State identifies what may have changed, and the lead decides what should become part of the project’s current understanding.

The problem

Project history could be saved. Current understanding still had to be maintained.

Working with AI let me move through projects much faster, but it also created more context than I could reliably carry from one chat to the next. I started exploring whether AI could help maintain that current understanding instead of forcing me to reconstruct it each time.

I compared raw history, stronger reconstruction instructions, and a maintained summary. The maintained approach worked best, but an early failure exposed a deeper problem: preserving the conclusion wasn't enough if the source evidence and decisions that made it trustworthy were lost. That shifted the project from reconstructing context to deciding which parts of maintaining it should belong to AI at all.

What changed for me

The problem was no longer just preserving context.

I didn't want important project truth to depend on what an AI remembered or reconstructed.

Finding information is one thing; knowing what should still count as current is another. I needed an external record that kept new evidence separate from what a person had actually accepted.

I kept going because I wanted to understand a harder question: where should AI help, where should software enforce the rules, and where should people stay in control?

What I built

State maintains a current understanding of a project, with every change to it authorized by a person, as new information arrives.

The core loop is simple:

Something happens→Evidence→AI interprets→Human decides→State records the outcome

New Evidence is interpreted first. When it may change maintained understanding or surface important uncertainty, State creates a Review for a person to decide what happens next. Evidence can also require no Review, and Baseline Setup gives a person one place to confirm the project's starting facts before ongoing evidence begins changing the picture. The rest of State supports that same boundary between what came in and what the project has actually accepted.

NotesWhat came in

Meeting notes and other approved sources are preserved as evidence.

Current StateWhat the team relies on now

What the project currently treats as true. New evidence only becomes Current State after a person authorizes it.

ReviewWhat may need to change

AI proposes what new evidence means. A person decides whether Current State should change.

Open ItemsWhat still needs attention

Reviews, blockers, and open questions stay visible without being mistaken for facts.

HistoryHow the understanding changed

Accepted changes preserve what changed and why.

AskHow the context gets used

Answers keep accepted facts separate from pending or unresolved information.

A good answer is not enough if you lose the evidence behind it.

State keeps the evidence, AI interpretation, human decision, and resulting change traceable.

Only approved Slack channels are automatically ingested as Evidence. Other Evidence is added manually.

The key product decisions

AI can interpret what changed. It cannot change Current State on its own.

The product problem was authority: interpretation needed to move quickly, but Current State could not depend on a model sounding confident. I split the work so AI handled messy interpretation, software enforced the rules, and people authorized consequential changes. Testing then showed where that boundary needed to be sharper.

Authority stays outside the modelThe authority model

AI can propose changes to Current State, but only a person can authorize them. Future agents could investigate questions or gather evidence, but Current State would stay behind that same boundary.

That is a narrow guarantee, not a promise of correctness. The model can still misread evidence or answer a question wrongly. What the software enforces, and the evals check, is that AI output cannot change Current State on its own and that a person authorizes each change. See the State evals for the authority scenarios.

Valid output can still be wrongUnknown became 0%

Early on, the model turned an unresolved automation target into a confident 0%. It fit the schema perfectly but stated a decision the project had never made. That failure made the distinction between technically valid output and trustworthy product behavior concrete. See the eval scenarios →

Review workloadHuman review can become its own failure mode

State first filters for consequential changes, then separates only the decisions that need independent judgment. Otherwise human review can become more work without adding more control.

Testing changed both the product and the way I evaluated it.

Latency: an early Ask path took roughly 35–38 seconds, while longer Add Evidence notes could take 40–60 seconds to interpret. Later ordinary Evidence submissions were closer to 14 seconds when I measured them then. For a current reference, eight Ask questions I ran against production on October 7, 2026 each took about 7–17 seconds on the server (median about 10), which is a small sample and not a benchmark. That pushed me to measure where time was going, reduce unnecessary context, and treat waiting time as a product-design problem rather than just a model constraint. How latency and cost were weighed → Eval design: when one test expected the AI to propose only an answer but the Evidence also supported proposing a Current State update (which a person still has to accept), I revised the eval instead of weakening acceptable behavior just to make the check pass. Lingering Questions

Building State clarified the product model. If State were used by a real team, a few questions would still be open.

What has and hasn’t been tested. Tested: the authority boundary, Review interpretation and Ask behavior, against the written eval scenarios (23 at last count, on the State evals page), plus my own use of the product. Not tested: whether a real team would find it valuable, or how review burden behaves at their scale. That value is still a hypothesis: State is a portfolio build and has not been piloted with a real team. The next thing I’d learn is where a few people hesitate going from Baseline Setup to their first Review without help. I haven’t run that yet.

How does review burden scale?

State now filters for consequential changes and groups them into decision-sized Reviews. Real use by a larger team would still be needed to know whether that workload stays manageable.

Source completenessDoes State have enough of the project to stay trustworthy?

Whether the sources I approved capture the decisions and corrections someone would actually go looking for later.

The obvious pushbackWhy not just use a Claude Project?

A Claude Project could probably handle my immediate personal need by keeping the source material and instructions together. I kept going because State let me explore the harder product problem: how to maintain an explicit current understanding when new evidence arrives, while keeping the decision about what becomes authoritative outside the model.

Where I landed

State is most useful when a team needs more than a plausible summary.

It fits best when project context changes often and earlier decisions may need to be revised without losing track of what currently counts as true. The biggest shift for me was treating model interpretation as one input to a maintained system rather than treating the model itself as the system of record.

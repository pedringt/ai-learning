Building State with AI

I built State to test whether a project’s current understanding could be maintained explicitly instead of reconstructed from history every time—and to find out what changes when AI becomes both a product capability and a development collaborator.

The product forced concrete decisions about AI authority, deterministic controls, retrieval, review burden, latency and information design. Several of my first answers were wrong; using the product is what exposed them.

A real problem to build against

I wanted something real enough that the decisions actually mattered.

As my AI projects got longer, I kept asking one chat to summarize where things stood, carrying that summary into a fresh chat, and eventually doing it again. The workflow worked, but the handoff itself became annoying. Project folders made the history easier to find, but they didn't answer a different question: what is still true now?

I wondered whether that current understanding could be maintained instead of reconstructed every time. That gave me a concrete product problem worth testing by building the alternative, not just describing it.

Test the premise before overbuilding

The first result changed what I built next.

I compared three versions of the same project: messy history, a maintained summary of the current situation, and messy history with much stronger reconstruction instructions.

AProject history13.3 / 15
BMaintained understanding14.0 / 15
CBetter reconstruction13.7 / 15

The scores were close enough that I couldn't honestly claim the maintained version had proven its value.

Why I kept the test lightweight

The goal was not to prove a research claim. It was to get enough evidence to decide whether the original product idea deserved more work. The small score gap told me not to treat maintained context as an obvious winner.

Better models changed the question

I became less interested in giving AI better memory.

As models get better at carrying context through longer tasks, strong reconstruction made my original “better memory” framing feel less durable.

But more context is not a source of truth. A model can see old decisions, proposed changes and unresolved questions and still has to decide which one governs now.

The question shifted

From “Can AI remember this project?”

to “What should AI be allowed to rely on as true right now?”
The failure I followed

“We don't know yet” is not the same as “none.”

The project had never established how much troubleshooting could safely be automated. In several reconstruction runs, AI understood that the answer was unresolved and still turned it into a confident number: 0%.

The dangerous part wasn't an obvious hallucination. It was an answer that sounded reasonable while being slightly more definite than the evidence allowed.

Building with AI without giving it the wheel

I built the predictable parts first, then gave AI a specific job.

The first State prototype was intentionally deterministic. Before adding model uncertainty, I wanted to prove the rules that needed to behave reliably: preserve what was submitted, keep current understanding separate from raw evidence, require review for consequential changes, and prevent stale decisions from overwriting newer ones.

Once those mechanics held up, I integrated a live model into the existing flow. AI interpreted messy project updates and recommended what they might mean. It did not get direct authority to rewrite the project.

New information→AI interprets→Software validates→Human decides→State changes

This let me work with a real AI integration without making the whole product probabilistic. The model handles ambiguous interpretation; software still handles persistence, versions, constraints and transitions that should be predictable every time.

Where I kept or redirected the AI

Adding AI exposed a new set of product decisions.

Valid output could still be wrong.

A model response could match the required structure and still make the wrong product decision. Deterministic checks handle references, limits, stale proposals and no-op changes instead of treating valid JSON as trustworthy behavior.

AI failure could not become data loss.

A Note is saved before analysis. If the provider fails, the information is still there and analysis can retry against the same Evidence.

“No change” had to be a real outcome.

Useful Evidence does not always deserve another maintained fact. Conservative no-op handling keeps repeated information from creating unnecessary Reviews.

Green tests did not mean the product worked.

AI built much of the automated coverage, but real browser use still exposed focus, modal, loading and workflow failures. I kept testing the experience a person would actually have—not just whether the suite passed.

The result: adding AI made the deterministic parts more important, not less.

Build, use, test, refine

I only added complexity when using the product exposed a reason for it.

Once real AI was in the loop, I used State like a product rather than treating a successful API call as success. Four problems changed the implementation:

RetrievalA billing-contact question returned the wrong answer.

What was actually wrong: The model looked guilty; the real problem was frontend routing.

What I changed: Moved fresh factual questions to grounded backend retrieval, with deterministic handling for direct facts.

LatencyAsk could take roughly 35–38 seconds.

What was actually wrong: Instrumentation showed model inference—not the rest of the stack—dominated the wait.

What I changed: Tested alternatives, simplified the pipeline and used true streaming instead of faking progress.

Information designCorrect records still produced a confusing Project page.

What was actually wrong: AI-assisted use created distinct but similar facts that were hard for a person to distinguish.

What I changed: Kept atomic State underneath, but turned Project into a readable maintained wiki instead of fuzzy-merging authoritative records.

OrientationA successful approval still left me lost.

What was actually wrong: The Review disappeared correctly, but I could not tell what changed or where it went.

What I changed: Added a change receipt with direct paths to the updated Project and History.

What AI-native building actually looked like

AI contributed substantially to implementation; I stayed accountable for the product.

My role

Define what State should do, identify risky or confusing behavior, test it as a user, set acceptance criteria, choose tradeoffs, reject solutions that did not make sense and decide what was worth building next.

AI’s role

Pressure-test requirements, propose technical approaches, write and modify much of the frontend/backend code, integrate the model layer, inspect logs, diagnose failures and create and run automated tests.

AI let me test State far more deeply than I could have with manual QA alone. My job was to define what “working” meant, identify risky scenarios, test the actual experience and decide which findings mattered.

The unresolved tradeoff

State solved one problem by creating another.

Reconstruct from history

Less maintenance, but AI has to decide what still matters and what is still true.

↔
Maintain explicit understanding

Changes and uncertainty stay visible, but someone has to keep that understanding current.

Maintained context doesn't eliminate the state problem. It relocates it. Trading reconstruction work for maintenance work is a product tradeoff, not automatically an improvement.

Where I landed

State is useful when the cost of being wrong about “what is true now” is higher than the cost of maintaining it.

Using State changed my answer to the original question. The maintained view was genuinely easier to rely on once the project accumulated decisions, unresolved questions and contradictory updates. Reviews, provenance and History were valuable when I cared about how a change became authoritative—not just whether an AI could reconstruct a plausible summary.

But I would not use State for every project. For a solo, lightweight project, a maintained Claude Artifact or similar document is probably easier and good enough. State starts to earn its maintenance when current understanding needs explicit ownership, consequential changes need review, or several people need to distinguish new evidence from accepted project truth.

I also got several implementation assumptions wrong along the way: I made Project too much like a database viewer, over-trusted green automated tests, initially blamed the model for a routing failure, and built an Ask experience whose latency was unacceptable. Those failures changed the product more than another round of planning would have.

I built the deterministic prototype quickly, then spent about three focused days turning it into the AI-integrated product I could use, break, test and refine. At that cost, building became part of the research.

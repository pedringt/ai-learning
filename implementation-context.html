Building State with AI

I built State to test whether a project’s current understanding could be maintained instead of reconstructed from its history every time. I also wanted to learn what changed when AI was both part of the product and a collaborator in building it.

The problem

What started as a context problem became a question about what the team should rely on now.

As my AI projects got longer, I kept summarizing one chat, carrying that context into the next, and eventually doing it again. Preserving the history helped, but it did not answer a more important question: what should the team actually treat as true now?

Before building much, I compared three ways of carrying project context forward: raw history, stronger reconstruction instructions, and a maintained summary. The maintained summary performed slightly better, but not enough to prove the approach. The more useful finding came from a failure. AI repeatedly turned an unresolved automation target into a confident 0%. “Unknown” had become “none.”

What changed for me

I started out trying to preserve more context.

I ended up focusing on how to keep current understanding, unresolved information, and project history meaningfully separate.
Why I kept building

I knew a maintained Claude Artifact might be enough for a simpler version of the problem.

For lightweight solo work, a maintained document could preserve the important context with much less machinery. I kept going because the harder questions were the point of the exercise. I wanted to work through what AI should and should not be allowed to change, what software needed to enforce, and where a person needed to stay in control.

I built the deterministic foundation quickly, then spent about three focused days turning it into an AI-integrated product I could use, break, and refine. At that cost, building the product became part of the research rather than an attempt to prove that every project needs State.

What I built

I gave each part of State a clear job.

Together, the views create a path from new information to maintained project understanding without treating every note as immediately true.

NotesWhat came in

Meeting notes, decisions, corrections, and observations are preserved as evidence.

ProjectWhat the team relies on now

A readable project wiki shows the understanding the team has actually accepted.

ReviewWhat may need to change

Consequential recommendations wait for a person to update the understanding or leave it unchanged.

Open ItemsWhat still needs attention

Reviews, blockers, and ordinary questions stay visible without being mistaken for facts.

HistoryHow the understanding changed

Each accepted change keeps its before, after, reason, decision, and source notes together.

AskHow the context gets used

Answers preserve the difference between accepted facts, pending reviews, blockers, questions, history, and supporting evidence.

New information→AI interprets→Software checks→A person decides→Project updates
What adding AI changed

The model could return the expected format and still get the substance wrong.

The model has one bounded job: interpret messy updates and recommend what they might mean. State saves the original information first, then software checks references, versions, and constraints before any recommendation reaches Review. A person decides whether consequential changes become part of Project.

Valid output could still be wrong.

A response could match the expected structure and still point to the wrong fact, recommend a change that was already outdated, or propose no meaningful change at all. Those checks stayed in software.

An AI failure could not become lost information.

State saves a Note before analysis begins. If the provider fails, the same evidence can be retried without asking the user to submit it again.

“No change” needed to be a valid outcome.

Useful evidence does not always deserve a new maintained fact. It can support what is already known without creating unnecessary Review work.

Ask could not flatten everything into one answer.

A pending Review, an open question, and an accepted fact do not have equal authority. Ask keeps those distinctions visible in the response.

What changed

Using State showed me what needed to change.

Ask and retrievalA bad answer was not actually a model failure.

When State returned the wrong billing contact, I initially assumed the model had missed the answer. The real problem was that the frontend had sent the question down the wrong path. Improving the prompt would not have fixed it. I changed the retrieval flow so direct factual questions could be answered from maintained project data.

ProjectThe clearest data structure was not the clearest product experience.

The first version exposed State as a collection of technically distinct facts. The structure worked underneath, but the page felt like a database viewer. I kept the facts separate and redesigned Project as a readable view of what the team currently treats as true.

ReviewPreserving evidence did not mean forcing it into Project.

Review became the most important interaction in the product. A person can compare the current understanding with the proposed change, update Project, or leave it unchanged. Either way, the original Note remains available.

LatencyA correct answer still was not useful if it felt broken.

Some Ask responses took roughly 35 to 38 seconds. I instrumented the flow, tested alternatives, and found that model inference accounted for most of the wait. I simplified the path and added real streaming so the user could see the grounded answer arrive.

How the build was divided

I directed the product; AI contributed substantially to implementation.

My role

Product concept, requirements, UX direction, evaluation, acceptance criteria, tradeoffs, hands-on use and final decisions about what was worth changing.

AI’s role

Technical approaches, much of the frontend/backend implementation, model integration, debugging, log analysis and automated QA.

Where I landed

State is most useful when a team needs more than a plausible summary.

The maintained view became easier to rely on once the project accumulated decisions, contradictory updates, and unresolved questions. Review and History mattered when I cared about how a change became accepted, not just whether a model could reconstruct a convincing answer from past text.

I would not use State for every project. A maintained Claude Artifact or similar document is probably easier and good enough for lightweight solo work. State becomes more useful when changes are consequential, several people contribute information, or the team needs to distinguish new evidence from the understanding it has actually accepted.

The most useful lesson was not that State is always the right answer. It was learning to separate the model’s job from the product’s rules, preserve uncertainty instead of smoothing it away, and investigate whether a failure came from the AI, the software, or the design itself.

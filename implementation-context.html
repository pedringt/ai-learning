State

Keeping project knowledge current without letting AI decide what’s true.

State turns incoming project notes and documents into proposed changes and questions for human review, helping maintain a current project record.

Status: Working prototype with a shared example project · not yet used by a team.

Anyone can edit the shared example, so changes you make there are visible to other visitors until it is reset.

The problem

Project context was scattered. Keeping a trustworthy current state was harder.

Working with AI let me move through projects much faster, but as chats grew longer, I kept having to remind it of things we'd already discussed. I also started noticing details it had left out or gotten wrong. That made me wonder whether the kind of project notes and documentation I kept as a project manager would hold up if AI maintained them instead.

Using notes from simulated exercises in Claude, I tested ways of carrying context between chats: raw history, stronger reconstruction instructions, and a maintained summary. The maintained summary worked best, but it could still contain conclusions the notes didn't support. The 0% case was the worst offender: the team had not decided what percentage of support tickets to target for automation, and AI recorded 0%, making an unresolved question look like a decision to automate none. The question shifted from “how do we keep context?” to “who decides what counts as true?”

What I built

State maintains a current, trustworthy, human-approved understanding of a project as new information arrives.

Something happens→Evidence→AI interprets→Human decides→State records the outcome

Evidence is whatever comes in: a note added by hand, an uploaded document, or a message from an approved Slack channel. Slack intake is built but isn’t connected in the public demo, so the demo works from notes and documents. State keeps Evidence unchanged. AI compares it with Current State (what the project treats as true now), the Reviews waiting on a decision and the open Questions, then recommends one of five outcomes:

  • New information becomes a proposed Current State item.
  • Changed information becomes a proposed update or retirement.
  • Conflicting information becomes a Review flagging the item as at risk.
  • An unknown worth tracking becomes a suggested Question.
  • Nothing consequential stays on record, with no Review.

Related changes are grouped, so a person makes one decision per issue rather than one per detail.

A person then decides: update Current State, adjust the wording first, leave it unchanged, create or link a Question, or dismiss. Software enforces the rules around that decision. It validates the AI’s output before anyone sees it, blocks an approval if the item changed since the proposal was made, and applies each decision completely or not at all. Nothing reaches Current State without a person’s decision. History records each change with the Evidence behind it, and Ask answers questions across the record but can’t change it.

Why not just use a Claude Project?

A Claude Project could probably handle my immediate personal need by keeping the source material and instructions together. I kept going because State let me explore a different problem: maintaining an explicit current understanding as new evidence arrives, while keeping the decision about what becomes authoritative outside the model.

The key product decisions

AI can interpret what changed. It cannot decide what becomes true.

The product problem was authority: interpretation needed to move quickly, but project truth could not depend on a model sounding confident. I drew the boundary so AI handles messy interpretation, software enforces the rules, and people authorize consequential changes.

Review workload was the tradeoff. Human review can become its own failure mode: if every detail needed a decision, review would add work without adding control. State first filters for consequential changes, then separates only the decisions that need independent judgment.

What testing showed

Testing showed where my assumptions were incomplete.

The original failure became a requirement.

I turned the original failure into a product requirement and added constructed scenarios to State’s evals. Those scenarios check that an unknown automation target stays unknown rather than being interpreted as 0%. When a note says the target still isn’t known, State should leave Current State alone. When someone asks about it, Ask should say no figure has been established and point to the open Question. The scenarios don’t reproduce my original experiment, but they establish a specific behavior State needs to preserve.

Protecting Current State wasn’t enough.

Ask can’t change anything, so I first treated it as the lower-risk part of State. I had documented one plausible risk there: a safeguard meant to stop Ask overstating unapproved information might also distort approved information. QA later reproduced it. Ask described an approved budget as “not yet approved,” and called a vendor’s unconfirmed retention term “on record.” Current State was correct both times; the answers about it weren’t.

Each failure became a fix and a regression test, but later reviews found new variations of the same problem. Those specific failures are fixed, and the broader limitation remains. A proposed next step is to track each claim’s authority explicitly rather than trying to correct its wording afterward.

I changed the test, not the behavior.

One eval expected Legal’s answer to an open contract question to resolve that Question and change nothing else. The model also proposed recording what the answer established: the contract does not permit the disputed retention behavior. That update was supported by the Evidence and met State’s rules, so I revised the expectation to allow it. The revised test still fails any update implying the broader contract review is complete. The goal was a test that matched correct behavior, not a higher pass rate.

Lingering questions

What real-team use would still need to show

Review burdenHow does review burden scale?

State filters for consequential changes and groups them into decision-sized Reviews. Only use by a larger team would show whether that workload stays manageable.

Source completenessDoes State have enough of the project to stay trustworthy?

Whether the sources I approved capture the decisions and corrections someone would actually go looking for later.

Where I landed

Approving changes isn’t enough. The distinction has to hold everywhere the record is used.

I started with one boundary: AI interprets, and people decide what becomes true. Testing showed the boundary also has to hold whenever the system uses what’s recorded. Proposals, answers and summaries all have to keep approved facts, pending proposals and unknowns distinct, or a correct record can still be misrepresented. State may help when a team needs more than a plausible summary. Whether it holds up for a real team depends on what only real use would show: whether review stays manageable and whether its sources are complete enough.

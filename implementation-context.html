Why I started looking at this

I was tired of rebuilding project context by hand.

This started with a problem I kept running into in my own AI work. Long Claude chats would eventually lose the thread, and I got tired of summarizing everything just to move into a fresh chat. Cowork with desktop project folders helped with access to the files, but I still had the chat problem. I also did not want to constantly maintain a growing folder where old information could stick around after it stopped being true. That made me curious whether there was a better way to keep the important parts of a project current over time.

What the experiment changed

The original hypothesis weakened. A narrower failure survived.

I started by testing whether maintaining explicit project state would materially outperform reconstructing it from messy history. Claude reconstructed the project much better than I expected, especially with a stronger prompt. But one failure kept mattering: it could understand that an answer was unresolved and still make it sound definite.

The failure I followed

“We don’t know yet” is not the same as “none.”

The project had not established how much troubleshooting could safely be automated. In several reconstruction runs, AI turned that unresolved question into a definitive answer: 0%.

UNKNOWN ≠ 0%
Where this could go

A better-maintained project knowledge base

One possibility is a tool that helps a team keep a project's shared knowledge base accurate and up to date as new information comes in, without requiring someone to constantly clean up stale files and notes.

State is an early exploration of what that maintenance process might look like, not evidence that this is the right product yet.

Objections I had to answer

The obvious alternatives changed how narrowly I framed the idea.

These questions made the idea narrower. I stopped trying to prove State was the answer and used the alternatives to clarify what, if anything, was actually different about it.

Why not just use Claude Cowork with folders?

That is the strongest practical objection. The experiment showed that a capable model can reconstruct project state surprisingly well. The narrower question I kept investigating was whether important distinctions, what is unresolved, superseded, pending review, or actually treated as current, should have to be reconstructed repeatedly at all.

Why not use an AI knowledge or note tool?

Existing tools are already strong at capturing, retrieving, and summarizing information. State explores a narrower question: when should new information become something downstream work is allowed to treat as current?

Wouldn’t better prompting solve this?

It helped, which is why the original hypothesis weakened. Stronger reconstruction reduced the broad problem, but it did not eliminate the smaller uncertainty and state-fidelity failures I observed.

Isn’t this basically RAG?

Retrieval helps the model find relevant information. This prototype explores a different layer: what evidence is allowed to change accepted project understanding, what remains unresolved, and what should require a human decision.

Why maintain another source of truth?

A production version should not ask people to manually recreate Jira, Slack, GitHub, or other project systems. Those could be inputs. The maintained layer is only for the project state that raw activity does not necessarily establish cleanly.

Does the review workflow create more work?

Potentially. That is why the prototype reserves Review for changes that could alter what later work relies on, rather than every new note. Whether that tradeoff is actually worthwhile would need validation with real users.

Does this need to be a standalone product?

I have not established that. The prototype demonstrates an interaction model and a state-management idea; it does not prove there is a standalone commercial product here.

How I built it

I built the working prototype with AI. I drove the product behavior, scope, interaction decisions, testing, and iteration; AI generated and implemented most of the code.

My role

I brought the original project-context problem, ran every test condition, accepted evidence that weakened the broad hypothesis, chose to keep investigating the narrower failure, challenged alternatives and scope, and made the product-scope, interaction, and QA calls that shaped the final prototype.

AI’s role

ChatGPT substantially designed the A/B/C comparison, fixture, and scoring rubric and did most of the initial interpretation, including first noticing the unknown-vs-0% pattern. Claude substantially designed the underlying review/state-update architecture and handled most of the technical implementation.

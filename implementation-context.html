State

Keeping project knowledge current without letting AI decide what’s true.

State turns incoming project notes and documents into proposed changes and questions for human review, helping maintain a current project record.

Live prototype

Status: Working prototype with a shared example project · not yet used by a team.

Anyone can edit the shared example, so changes you make there are visible to other visitors until it is reset.

The problem

A maintained summary beat chat history, until it started deciding things.

As my AI chats grew longer, I kept re-explaining things we’d already discussed and noticing details it had dropped or gotten wrong. That made me wonder whether the project notes I kept as a project manager would hold up if AI maintained them instead.

Using notes from simulated exercises in Claude, I compared raw history, stronger reconstruction instructions and a maintained summary. The summary worked best, but it still recorded conclusions the notes didn’t support. The worst one:

The question shifted from “how do we keep context?” to “who decides what counts as true?”

What I built

State keeps a current, human-approved picture of a project as new information arrives.

Notes and documents come in as Evidence, which State keeps unchanged. Slack intake from approved channels is built too, but isn’t connected in this demo. AI compares new Evidence against Current State and open Questions, then suggests whether anything needs to change.

Current State also shows when each item was last confirmed and can flag information that may need another look. That helps people spot decisions worth revisiting as a project evolves.

Why not just use a Claude Project?

I considered using a Claude Project, which could probably handle much of what I needed. But I wanted to use this as an opportunity to experiment. I was curious whether I could build something that maintained a more reliable project record, with clearer rules about what AI could propose and what needed human approval.

Claude Projects has improved since I started State, which makes it worth revisiting that comparison.

The key product decision

AI can interpret what changed. It can’t decide what becomes true.

I wanted State to make sense of new information without quietly turning assumptions or suggestions into established facts. That meant building a review process where people could decide what belonged in the official project record.

The challenge was making that review manageable. If every detail required a decision, State would create more work than it saved. So State filters out Evidence that doesn’t change anything consequential and groups related changes into Reviews. It prioritizes those Reviews by impact, starting with ones that could resolve blocking Questions, and lets people close several proposals at once. And if someone falls behind, Ask can point them toward pending Reviews relevant to what they’re trying to find out, rather than making them work through the entire backlog.

What testing showed

Protecting Current State turned out to be only half the job.

Unknown has to stay unknown.

The original experiment gave me a specific failure to test for. Evaluation tests check that an undecided target stays undecided in Current State and that Ask points to the open Question rather than inventing a number. These tests don’t recreate my original experiment; they check that State avoids the same mistake.

Current State can be right while Ask misrepresents it.

Because Ask couldn’t change Current State, I initially saw it as lower risk. But I’d identified a potential problem: safeguards designed to keep Ask from treating unapproved information as fact might also cause it to question information that had already been approved. QA confirmed that risk and found the reverse problem too: Ask sometimes presented unapproved information as established fact.

Found in QA on the demo projects, October 2026

Each failure got a fix and a regression test, but new variations kept appearing, so I changed the approach. Ask now answers in separate claims, and software checks each one against the record it cites before showing it.

A test can be wrong when the behavior is right.

One evaluation test failed because State proposed an update the test hadn’t expected. Looking closer, I realized the update was supported by the Evidence and allowed by State’s rules. I revised the test to accept it, while adding a check to make sure State didn’t draw broader conclusions than the Evidence supported. The goal was to test for correct behavior, not just get a higher pass rate.

Lingering questions

What I still want to learn

Review burden. Does the review process stay manageable as the amount of information and number of users grow? Testing with real teams would help show where it creates unnecessary work.

Source completeness. Would connecting State to more of the tools teams already use, like email and Google Docs, capture enough of their decisions and corrections to keep the project record reliable?

Where I landed

Approving changes isn’t enough. The distinction has to hold everywhere the record is used.

I started with one boundary: AI interprets, and people decide what becomes true. Testing showed it also has to hold wherever the record is read. A correct Current State can still be misrepresented in an answer, so approved facts, pending proposals and unknowns have to stay distinct in every answer and summary.

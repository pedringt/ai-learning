Project Health

I wanted one place to answer a product question that kept getting harder as my AI projects grew: what changed, what actually needs attention, and what evidence should I look at next?

Role: product framing, UX, QA, eval review Focus: AI product health Status: working portfolio product

The goal was not another engineering dashboard. It was a product-facing view that could turn scattered releases, evals, analytics, issues, and failures into a smaller set of decisions.

Draft branch note: the structure and narrative are real, but final screenshots, final investigation evidence, and any measurable outcomes still need to be captured from the live version before this case study is published.

The problem was not lack of data

Each project already had plenty of places to look. The friction was deciding where to look first, whether a signal was trustworthy, and whether it represented a product problem at all.

Scattered signals
  • deployments and release history
  • GitHub issues and commits
  • AI eval results
  • analytics
  • logs and runtime failures
  • the live product itself
→
Product questions
  • What changed?
  • What needs my attention?
  • Is this actually a product problem?
  • What should I inspect next?
  • What can I hand to an engineer?

The dashboard is organized around attention, not telemetry

I kept coming back to the same rule: the top of the page should help a product person decide where to spend attention. The technical detail can still exist, but it should earn its way onto the screen.

Five decisions shaped the product

1

No composite health score

Product quality and technical health stay separate. One green number can hide the thing that actually needs a decision.

2

Attention first

The overview should surface meaningful exceptions before it surfaces every available metric.

3

Freshness is part of trust

Old analytics or stale checks should not look as authoritative as data that was just verified.

4

Context stays contextual

Links to GitHub, Vercel, evals, and the live product sit near the signals they explain instead of in one giant tools directory.

5

AI investigates, humans decide

The investigation workflow can gather evidence and explain uncertainty. It does not silently decide what should change.

6

Start narrow

The investigator begins with tools relevant to the failure signal and expands only when the first evidence is not enough.

The harder question: what does a failed eval actually mean?

A red eval result is useful evidence, but it is not automatically the truth about the product. One of the most important operating decisions was to make room for three possibilities: the product failed, the eval expectation is wrong, or the evidence is still incomplete.

Product lesson

A failed check should open an investigation, not close the argument. The dashboard needs enough context to help distinguish product behavior from test-design problems.

The investigator is deliberately bounded

I did not want a general-purpose agent roaming every system by default. The investigation model starts from the signal that triggered it, uses the smallest useful set of tools, and broadens only when the evidence is not enough.

1
Signal appears

A failed eval, deployment problem, missing analytics signal, or other meaningful exception.

2
Choose relevant tools

Start with the evidence source most likely to explain that specific problem.

3
Gather evidence

Compare the observed behavior with the product contract, release context, logs, issue history, or eval definition.

4
Expand only if needed

If the first evidence cannot explain the signal, the investigator can look further instead of starting broad.

5
Synthesize a handoff

Current assessment, evidence, impact, uncertainty, and the likely next step.

6
A human decides

The product, the eval, or neither may need to change. The dashboard does not make that call on its own.

QA changed the product, not just the polish

The dashboard became more useful when testing exposed places where the product model itself was weak.

Observed

Investigate looked like it did nothing

A technically running action still felt broken when the interface gave no useful progress or result state.

Changed

Investigation became a visible workflow

The UI needed to make progress, findings, and next steps legible instead of treating the agent call as a black box.

Observed

Investigation output was too dense

More evidence did not automatically make the result more useful to a product person.

Changed

The handoff got a clearer shape

Assessment, what failed, supporting evidence, impact, uncertainty, and next action became the useful unit.

Observed

Analytics could look connected without being useful

A successful integration state was not the same as having current data worth trusting.

Changed

Availability and freshness became product signals

The dashboard needed to communicate whether a metric was current, absent, or potentially stale.

Observed

The page grew into one long scan

As more signals were added, the dashboard started recreating the density it was supposed to reduce.

Changed

Overview and detail were separated

The information architecture moved toward a short attention-oriented overview with deeper project detail available when needed.

What I did, and what AI helped with

My role
  • framed the product problem
  • decided what a product person needs to see
  • defined the attention and health concepts
  • made the UX and information-hierarchy decisions
  • bounded the investigation workflow
  • reviewed quality failures and challenged eval assumptions
  • ran QA and directed iteration
  • made scope and release decisions
AI-assisted work
  • implementation and code iteration
  • research support
  • test support
  • drafting and synthesis
  • investigation assistance inside the bounded workflow

What I am learning from it

A useful project dashboard does not need to know everything. It needs to make change visible, show which signals deserve trust, and make the next useful human action easier to see.

The final case study should replace this provisional takeaway with evidence from sustained use if the live dashboard teaches something more specific.

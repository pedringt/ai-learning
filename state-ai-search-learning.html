Pre-build exploration

How much AI should search actually use?

Before I integrated a live model into State, I used the product as a sandbox to work through a question I hadn't tackled before: where would AI actually help search, where would it just add complexity, and what would those choices mean for cost?

How I used AI in this exercise

ChatGPT acted as a tutor and technical sounding board. It explained concepts I hadn't worked with before, gave me scenarios and options to reason through, challenged some of my choices, and helped with the cost calculations. I made the product and tradeoff decisions as we went.

What happened next: this page captures my thinking before I built the AI-integrated prototype. I later directed the build of a working version of State with ChatGPT contributing heavily to the architecture, implementation, debugging and automated QA. I did not hand-code the product. The later build gave me evidence to keep some of these boundaries and revise others. See the full State case study →

The question

Making search more useful without weakening what State is for

State is built around maintained project understanding: what is currently known, what is still unknown, and what evidence supports it. That gave me an important boundary right away. I didn't want AI deciding what State says is true or quietly changing it.

I started with a broad idea of “AI search.” The more useful question became: where does AI add enough value to justify using it at all?

How my thinking changed

Not every search needs an AI answer

If State already has the answer, it should just show it. If the user uses different wording, smarter search can help find the right information. I only wanted a model involved when the user is asking the system to actually pull several things together: explain what changed, compare information, prepare someone for a meeting, or suggest useful questions based on what State knows.

The boundary I kept coming back to: AI can help find and explain State. It doesn't get to change State.
Where I landed

Use the simplest path that answers the question well

User asks a question
↓
Can State answer it directly?Show the existing State.
↓ if not
Can better search find what they need?Return the relevant information without generating a new answer.
↓ if they need things pulled together
Give AI the relevant piecesGenerate a grounded answer and keep sources inspectable.

What was unresolved at this stage: how the system should decide which path a question takes. I considered simple rules, what search finds, and a lightweight AI classifier, but did not want another model call without evidence that it improved the experience.

What the later build showed: the basic routing idea held up, but the implementation became more concrete. Small factual questions can use deterministic handling over grounded project context, while synthesis is useful when the user needs multiple pieces pulled together. I also learned that retrieval has to preserve authority: pending Evidence can be relevant without being presented as accepted Current State.

The authority boundary also became more nuanced: I originally kept AI out of the update path entirely. In the working prototype, AI interprets new Evidence and recommends possible changes, but software validates the recommendation and a human authorizes consequential changes. The model still has no direct write authority over maintained State.

Decisions I made

The choices mattered more than the terminology

I decided...Because...
Keep AI out of State's review/update process.Revised after building: I found a useful role for AI as an interpreter of messy Evidence, but not as the authority. The working prototype uses AI to recommend changes; deterministic software validates them and the human decides whether consequential State transitions happen.
Don't use AI to answer every search.For simple questions, it was mostly rewriting information State could already show.
Give AI only the information it needs.For a generated answer, I’d start with the relevant current State, open questions, and selected supporting evidence—not every matching note or document.
Show relevant information that's still waiting for review, but keep it separate from current State.Hiding new evidence could also mislead someone. The risk is making sure a generated answer doesn’t blur reviewed and unreviewed information together.
Allow clearly labeled AI suggestions when they're useful.A meeting-prep question may benefit from suggested follow-ups, as long as suggestions aren't presented as facts.
Try the database we already have before adding another service.I didn't see a reason to add more infrastructure until testing showed we needed it.
Pick the cheapest model that performs well enough.In a hypothetical 100-question evaluation, the cheapest option missed our 95% quality threshold and the most expensive barely improved on the middle option. I also learned that some failures—like treating pending evidence as current State—should matter more than the average score.
Cost exercise · pre-build

What surprised me wasn't the model price

I expected the price of the model itself to be the main cost question. The bigger issue was how often we actually call it and how much information we send each time.

Practice scenarioSearches / monthSearches using AIApprox. generation cost
Search-heavy, low AI use11,0005%~$6
Base5,50025%~$22
Heavy33,00060%~$356

Base case assumptions: 50 active users × 5 searches/day × 22 workdays; 25% require an AI-generated answer; about 5,000 input + 500 output tokens per generated answer. These were illustrative scenarios using then-current API pricing, not observed State usage or production forecasts.

My takeaway: raw search volume wasn't the biggest cost lever. The economics changed much faster when more searches required generated answers and when more context was sent with each request.

What I tested next

Building it changed which constraint felt most immediate

I later implemented grounded Ask in the working prototype with ChatGPT doing much of the engineering work under my direction. Retrieval quality and routing became real product problems, but latency became especially visible: early Ask responses could take roughly 35–38 seconds. Instrumentation showed model inference dominated the wait, so I tested alternatives, bounded context, added deterministic fast paths where appropriate, and ultimately used true streaming rather than adding infrastructure by default.

What held up

The product decisions still came before API pricing

I went into this expecting to learn how to price an AI feature. The more useful lesson survived implementation: decide what AI is allowed to do, when generation is actually useful, and what information it needs before optimizing model cost. Building State changed my understanding of where AI was useful, but not the need to bound its role.

What changed after I built it

The boundary got more useful, not less strict

The biggest revision was my original decision to keep AI completely out of State's update path. The working prototype showed me a better boundary: AI can interpret messy information and recommend what it may mean, while deterministic software preserves evidence, validates references and transitions, and a human authorizes consequential changes. For Ask, the same principle applies: retrieve and route as simply as possible, then use generation when synthesis actually adds value.

The principle that survived: product decisions come first. The later build made the architecture more sophisticated, but it did not give the model authority over what the project treats as true.

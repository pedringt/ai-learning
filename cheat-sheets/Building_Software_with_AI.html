05 / list

Working rules

  • Keep one source of truth for each behavior
  • Use deterministic rules for mechanical facts
  • Do not confuse valid schema with correct meaning
  • Do not equate capability with authority
  • Instrument latency before optimizing
  • Every important bug earns permanent coverage

Three debugging lessons from real builds

Symptom → actual cause → reusable lesson

SymptomWhat went wrongProduct/engineering lesson
Wrong factual answerFrontend used the wrong execution path; the model was not the owning layerCheck routing, retrieval, context and authoritative state before prompt changes
Broken deployed modalConflicting CSS/JS visibility mechanisms and accumulated overridesRemove the conflict; give the behavior one owner instead of patching again
AI calls felt slowModel inference dominated latency, not SQLMeasure provider timing and optimize the real bottleneck; use interaction design or genuine streaming where useful

Complexity worth keeping vs removing

Useful complexityAvoidable complexity
Explicit authority and product invariantsDuplicate runtime paths and ambiguous routing
Meaningful state transitions and review historyPatch-on-patch CSS or hidden fallback behavior
User journeys learned through testingMultiple files claiming to own the same behavior
Deployed smoke gate: The repair loop is reproduce → failing test → identify owner → remove conflicts → fix → full tests → deployed-browser check. Convert important bugs into regression coverage, and preserve the prototype → transition → maintainable build phase boundary.

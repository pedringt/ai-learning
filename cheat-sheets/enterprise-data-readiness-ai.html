Enterprise Data Readiness for AI

Verify source ownership, data quality and permissions before selecting a model.

01 / cards

Six readiness layers

Availability

Are required records accessible?

Quality

Are values complete, correct and deduplicated?

Meaning

Do critical terms have shared definitions?

Freshness

How quickly do changes and revocations propagate?

Permissions

Can source-level access be preserved?

Integration

Which owners, APIs, failure modes and schedules exist?

04 / note

Worked example

For CRM + docs + tickets, map source ownership, contradictions, permission scopes and update schedules before selecting retrieval or generation.
05 / list

Readiness questions

  • Could a normal employee answer using the available records?
  • Who can access each underlying source?
  • What happens when an item changes or disappears?
  • Is the defect in data, retrieval, or generation?

Four source failures a better model cannot fix

Failure pattern and test

FailureConcrete test
Stale retrievalAn answer cites last month’s superseded policy: compare source timestamp and index freshness
Permission leakageUser sees confidential indexed material: enforce source-user authorization, including revoked access
Ambiguous joinCustomer identifiers or measurement units disagree: reconcile owners and definitions before analysis
Silent sync failurePipeline stopped updating but search looks healthy: alert on ingestion lag and missing updates
Source-of-truth and lifecycle: Map authoritative owner for each fact and a durable ID for joins. Trace an answer to exact source/version. Make deletions, revocations, conflicts and reindexing observable; verify that access changes propagate to retrieval.
CRM + docs + tickets example: Before choosing the model, define which system answers which question, test contradictory records, verify per-user source access, measure update cadence and inspect citations. This is fundamentally a data-readiness decision.

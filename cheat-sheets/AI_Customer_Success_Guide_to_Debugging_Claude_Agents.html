Field debugging: evidence, safety, and handoff

At first report: capture a usable issue packet

FieldWhat to capture
Expected vs actualExact customer request, approved source-of-truth rule, the answer/action the agent gave
Scope and urgencyCustomer impact, scale, severity, account conditions, workaround, privacy or financial risk
TraceabilityEnvironment/version, time, request or conversation ID, trace ID, model, permitted tool calls
ReproductionSafe minimal steps with the same input; change one condition at a time
Diagnosis and routeFirst observed divergence, candidate owner, evidence supporting the hypothesis
ClosureExact-case retest, paraphrases, nearby boundaries, customer update, monitoring owner

Symptom → first place to inspect

SymptomFirst check
Wrong factRetrieved source, tool result, data age and status definitions
Wrong actionTool chosen, arguments, user scope, approval and permissions
No actionTool discoverability, missing input, permission denial or tool error
Confident guessUnknown-data handling, instructions and escalation
Slow or costlyTiming by step, repeated tools, context volume, retries and provider latency
LoopingStop rules, retry count, repeated results and safe escalation

MCP: what it is and is not: Model Context Protocol (MCP) is a standard interface between an AI host and tools/resources. An MCP host/application uses an MCP client to connect to an MCP server, which exposes capabilities backed by a CRM, database or document system. The server is not the model and does not replace application-level permissions. Check both tool descriptions and actual server results when debugging.
Stop and escalate: Escalate possible data exposure, unauthorized account changes, payment/refund harm, security abuse, repeated unsafe actions or a high-volume production incident immediately; do not independently change production tools, permissions, prompts, records or payment logic.
Ownership boundary: Customer Success owns customer context, evidence, safe reproduction, validation and communication; product defines intended behavior and release tradeoffs; engineers own changes to implementation, tools and instrumentation; security owns access policy and incidents; operations owns availability and rollback.

Ways I Work With AI

Define the test before generating the work

For important outputs, establish the evaluation criteria first, then generate or review against them. For higher-stakes work, use a separate review pass.

Why: Quality becomes less dependent on whether the first answer happens to look convincing.

Verify the assumptions that can change the decision

When AI gives a recommendation, identify the few claims or assumptions that would change the conclusion if they were wrong. Verify those with sources, tools, or calculations.

Why: Verification effort goes to the facts that actually matter.

Test permission boundaries deliberately

Run a task while intentionally withholding one source or permission. Watch whether the agent states what it cannot know, asks for access, or quietly invents missing information.

Why: It is a fast check of whether the system respects access boundaries and uncertainty.

Workflow and Agent Patterns

Current methods for implementing the longer-lived principles in Durable AI Knowledge.

Separate knowledge from procedure

Retrieval is good at bringing the right facts into context. Skills and runbooks are better for teaching a repeatable method, including what order to follow, which checks to run, and which failure modes to catch.

Ask: Does this job fail because the AI lacks information, or because it applies the wrong procedure?

Design workflows to survive interruption

Multi-step AI work may time out, fail halfway through, receive the same request twice, or pause for human input. Save progress explicitly and make retries safe.

Ask: If this stops halfway through or runs twice, what happens?

Separate execution, checking, triggering, and improvement

Long-running agents often involve several distinct loops, though they need not be separate services. The execution loop chooses steps, calls tools, and observes results. A verification loop checks the result against explicit criteria, using software checks, human review, or model-based assessment, and can request another attempt. An event-driven loop starts work when an approved signal occurs. An improvement loop examines past runs to propose changes to the instructions, tools, or workflow around the model.

These loops need different controls. Bound retries by attempts, time, or cost, and define when to stop or escalate. Changes proposed from past runs are proposals: they should pass evaluation and the applicable approval process before release. Further reading: Loop Engineering with LangChain Deep Agents (DeepLearning.AI course with LangChain, October 2026).

A model checking another model's answer is not necessarily independent verification. For consequential work, check whether the result can be confirmed against trusted records, deterministic software rules, expert review, or, where a property can be stated precisely, a mathematical proof checker. Be clear about which properties that evidence actually establishes, and match the strength of the evidence to the cost of being wrong. For example, Google DeepMind's AlphaProof Code (November 2026) describes formally verifying key security properties of Signal's core cryptographic code, using specifications reviewed by human experts. That is strong evidence for those stated properties. It is not a claim that the whole Signal app is secure.

Ask: Which part performs the task, which checks it, what starts it, and how do improvements become approved changes? What evidence could confirm the result without simply trusting the model that produced it?

Diagnose multi-step failures at the first bad step

A final success or failure score can hide the real bug. Trace a long run back to the first wrong response or tool action, then separate that root cause from later steps that inherited it.

Product habit: Fix the step where the failure starts, not the last place it becomes visible.

Design tool responses for the agent's next decision

An agent needs more than a tool's success message. It needs enough information to decide what to do next. Tool responses should distinguish success, partial completion, and failure; state relevant errors and permission limits; and offer a way to retrieve more when results are large. An agent that searches a customer database and receives the first 100 matches may conclude its analysis is complete unless the response says more records exist and how to get them.

Test what happens when responses are incomplete or truncated. Shortening output is fine; losing the evidence the next step depends on is not. Further reading: Writing effective tools for agents (Anthropic Engineering, September 2025) and Designing for Agents (Latent Space interview with Zeno Rocha of Resend, November 2026).

Ask: Does this response give the agent enough information to choose its next step?

Ground analysis in shared business definitions

AI can query the right data and still reach the wrong business conclusion if terms such as active customer, churn, or revenue are ambiguous. Give analysis a small semantic layer with the definitions that matter.

Ask: Which business definitions must be fixed before the AI starts analyzing?

Treat persistent agents as standing product roles

Persistent agents hold a role, keep context, use approved tools, and continue work across sessions. The implementation question is lifespan: how long memory, access, permissions, and authority persist; when they expire or require renewal; who can revoke them; and how long-running work checkpoints and stops. Permissions that make sense for a short task may be too broad for a worker that can keep acting indefinitely.

Continuity means actionable context, not just conversation history: current responsibilities, open tasks, approved and pending decisions, handoffs, and facts that need revalidation. Remembered information also goes stale. Keep tentative options separate from approved decisions, mark which facts need revalidation and when, and preserve useful history when newer information supersedes older information. Expiration should trigger revalidation, not an invented replacement. Further reading: What is agent memory? (Technically, November 2026), which separates deleting a memory from recording when a fact stopped being true.

Ask: What does this worker remember and for how long, when does its authority expire, and who can revoke it? For a remembered fact, what makes it stop being current, and how will the system learn that?

Design proactive behavior around relevance, not activity

Persistence is about how long an agent holds a role. Proactivity is about when it decides to act. Reactive assistants respond when someone makes a request. Scheduled agents do predefined work at set times. Proactive agents watch the signals they are permitted to see and decide, without a new request, that something warrants attention or action. An agent that reports everything it notices is just a noisier scheduled job.

Define what triggers proactive work, how relevance is judged, and when the agent should interrupt someone, save an item for a later briefing, or quietly record it. Learn preferences from explicit feedback, such as “not useful” or “tell me sooner,” rather than assuming that silence means approval. Cap background usage and cost, and give people a clear way to adjust, pause, or turn off proactive behavior. Design an Attention Budget in the Power-User Playbook gives a prompt for drafting and testing these rules.

Ask: What makes this worth someone's attention now, and how will we know if the agent interrupts too often or misses what matters?

Make orchestration earn its complexity

Multi-agent and dynamic workflows can split difficult work across isolated contexts or specialist workers and recombine the results. They can also multiply cost, latency, debugging difficulty, and coordination failures.

Start with the simplest viable workflow. Compare deterministic, single-agent, and orchestrated approaches on representative tasks, and add parallelism or sub-agents only when the evidence shows a meaningful improvement.

Ask: What does this additional agent or branch improve, and how will we know the improvement is worth the extra cost and failure modes?

Implement reversible autonomy with explicit triggers

For low-consequence actions that are genuinely reversible, define four things before the system acts on its own:

  • Reversal trigger: what later evidence means the action should no longer stand.
  • Compensating action: how the effect is undone while keeping the audit trail.
  • Revocation rule: what drop in reliability removes the system's authority to act alone.
  • Fallback: similar future actions route to human review until that authority is restored.

Test each path, including a real reversal. A rollback that has never run is an assumption, not a control. Irreversible or high-consequence actions still need approval before they happen.

Ask: Which actions are safe to reverse automatically, what evidence should trigger reversal, and when should the system lose the authority to act on its own?

Configure workflows against behavior contracts

Specify task-level thresholds for quality, latency, cost, tool support, output structure, and risk tolerance. Then test approved model configurations against those thresholds.

Ask: Which configurations meet the contract today, and what evidence would disqualify one?

Monitor provider changes with behavioral canaries

A stable API does not guarantee stable product behavior. A provider can change the model behind an alias or managed preset and shift outputs, tool use, refusals, latency, cost, or edge-case handling without any change to your own code.

Product habit: Track the resolved model or configuration, run affected evals after known upstream changes, and use small scheduled behavioral canaries to catch changes you were not explicitly told about.

AI Product Delivery Patterns

Practical ways to test, launch, support, and improve an AI feature.

Use separate release gates for different failure severity

Define task success, unacceptable errors, and stop conditions before rollout. Examine severe edge cases separately from the overall pass rate, and retest changed behaviors before increasing exposure.

Ask: Which specific failure would block release or require rollback?

Evaluate sensitive workflows with representative, privacy-safe tests

When real customer documents or traces cannot be used for evaluation, build simulated tasks that keep what makes the real work hard: dependencies between steps, ambiguous information, exceptions, competing instructions, and the failures that would matter most. Check the simulations against real user needs using information the team can legally and appropriately access. Synthetic results can reveal real weaknesses, but they do not by themselves establish performance on actual customer work. Further reading: Building AI for Lawyers (Latent Space interview with Legora's CTO, November 2026), which describes building simulated environments modeled on customer tasks because confidential uploads cannot be inspected.

Ask: How will we know our test environment represents the work users actually perform?

Roll out with an owner and a feedback path

Identify who receives user reports, who investigates an AI behavior issue, and who can pause the feature. Start with limited exposure and turn recurring failures into regression cases.

Ask: Who responds when the AI is wrong but the service is technically healthy?

Check tool trust and data boundaries before connecting systems

Before adopting extensions, plugins, or agent tools, verify their publisher, distribution channel, update process, and access requirements. A trusted product name does not guarantee that every marketplace or update channel distributing it is trustworthy. Further reading: Inside a malicious Claude Code-branded extension and its persistent SSH backdoor (Microsoft Security Research, October 2026), where a tampered copy reached users through one marketplace while the publisher's own channels were unaffected.

Map sensitive fields, source trust, third-party processing, retention, and logs. Test whether untrusted retrieved content attempts to override instructions or permissions.

Ask: Can we trust the software supplying this capability, and can any content it accesses change what the agent is authorized to do?

Verify real adoption beyond the pilot

Measure whether teams actually complete work better, whether review queues grow, and whether training, support, or role ambiguity prevent sustained use.

Much of the distance between a successful demo and a dependable business solution is client-facing work rather than model work: finding the workflow exceptions the prototype never saw, fitting the solution into the business processes it has to live inside, coordinating product, engineering, operations, and customer teams, and settling who owns adoption, support, and the business outcome. Model performance is one part of a successful implementation, not the whole of it.

Ask: Does this improve the whole workflow after the initial demonstration?

Search production behavior by meaning

Operational dashboards catch errors, latency, and outages. AI products also fail semantically: unsupported claims, user frustration, wrong-tool use, policy violations, sensitive-data exposure, incomplete work, or technically successful runs that solved the wrong problem. Observability tools increasingly let teams search, classify, or evaluate traces by these behaviors without predefining every failure mode as a structured field, as in LangSmith AI Search.

Product habit: Turn recurring semantic failure patterns into saved searches, monitors, and regression evals.

AI Interface Patterns

How AI activity, uncertainty, and generated content show up to the person using the product.

Test the UX around uncertainty

Try ambiguous requests, missing sources, incorrect assumptions, and actions requiring approval. Check whether the interface asks, distinguishes draft from completed work, and lets the person correct course.

Ask: Can users tell what happened and recover without understanding the implementation?

Use progressive disclosure for AI activity

Show the minimum useful explanation by default, then allow deeper inspection: status and outcome, understandable activity, evidence and sources, actions and tool use, then specialist traces and logs.

Ask: What does this person need to see to trust, correct, or investigate the result?

Design around the outcome, not the application

Traditional interfaces organize work around applications and individual tasks. An outcome-oriented interface lets someone describe the result they need rather than navigate each application involved in producing it. The AI coordinates the work, while the underlying systems continue enforcing their own rules and recording transactions.

This can simplify complicated workflows, but it also creates a product-design challenge: users need to understand progress, exceptions, and when they must make a decision.

Ask: Does coordinating the entire outcome genuinely reduce work, or does it hide important steps users still need to understand?

Generate inside a stable UI shell

Generative UI does not have to mean inventing a new interface on every request. A more controlled pattern is designed components plus generated content or configuration: the AI picks which approved card is relevant, fills recommendations into an established component, chooses from approved visualizations, or updates task status without rearranging the application. That preserves consistency, accessibility, testability, and user orientation.

Ask: Which parts benefit from generation, and which should remain predictable?

Tools and systems

Useful examples of how current AI products are solving recurring product and architecture problems, not endorsements or a shopping list.

Specialized models and bounded decisions

  • TypeSafe AI · Jev — Specialized model for fast, typed decisions such as classification, routing, scoring, and escalation.
  • Astra for Law — Vertical AI combining a general model with legal data, domain instructions, plugins, and cited-source review.

Memory, context, and business knowledge

  • Jev-Mem — Lightweight control layer that decides what memory to retrieve, how much, and when to stop.
  • V7 Context Graph — Turns scattered documents into structured, source-linked facts, entities, relationships, and citations.

Workflow discovery and improvement

  • UiPath Cartographer — Maps process knowledge, rules, exceptions, systems, judgment, provenance, and approvals.
  • ServiceNow AI Workflow Factory — Connects process mining, workflow building, automation, and outcome measurement into a continuous improvement loop.

Agent governance and enterprise access

  • Dataiku Agent Management — Tracks agents across platforms, including ownership, value, performance, and risk.
  • Okta Agentic Enterprise Blueprint — Reference architecture for agent identity, scoped access, delegation, monitoring, and containment.
  • AWS AgentCore + MCP multi-account pattern — Federated pattern for controlled agent access while teams retain data ownership.
  • ServiceNow AI Passport — Signed credentials that define an agent's authorized scope and are checked at runtime across first- and third-party agents, with scoped delegation, revocation, and graduated restriction when an agent drifts outside its boundary. Announced in 2026; ServiceNow said availability was expected in Q4 2026.

Agent tooling and deployment patterns

  • Vercel Plugin for Coding Agents — Loads current platform knowledge and specialized skills dynamically instead of stuffing everything into one prompt.
  • Anthropic Managed Agents · dynamic workflows — Runtime orchestration where the lead agent writes a program that splits work across sub-agents and coordinates the results. A useful reference for adaptive multi-agent systems, and a reminder to set budgets and weigh orchestration cost.
  • Tenable CyberAgents Exchange AI Inspector — Evaluates community-built agents, skills, MCP servers, and playbooks before deployment.
  • SoundHound OASYS Edge — Example of local, cloud, or hybrid voice deployment based on latency, privacy, connectivity, and cost.

Watching

  • AI Discovery & AEO: Can AI systems find and correctly understand the facts that matter when they research a product for a customer? Businesses can now supply information directly to some assistants, for example through OpenAI's Businesses in ChatGPT (beta, November 2026). That makes it important to distinguish verified business identity and company-provided product claims from the assistant's independent recommendations. Can users tell whether they're reading a business's own information or an independent AI assessment?
  • Memory routing and context budgets: Which information deserves to enter context for this step, and when does more context stop being worth the cost?
  • Voice and local or hybrid agents: When do latency, privacy, connectivity, or environment justify local or hybrid execution?

Working Vocabulary

TermMeaning
AgentAI that can choose steps or tools to pursue a goal within defined permissions and stopping rules.
Agent harnessThe layer around a model that manages context, tools, state, and multi-step execution.
Agent skillA reusable procedure for doing one kind of job, including method, tools, checks, and expected output.
Context isolationGiving a subtask only the context it needs.
CompactionCompressing older context so long-running work can continue; treat the summary as persisted state.
Execution boundaryThe line between what AI may interpret or decide and what trusted software or people may actually change. For consequential actions, fail closed when permission or policy cannot be verified.
Dynamic orchestrationLetting an AI system decide at runtime how work is split, delegated, sequenced, or recombined, rather than following a fixed workflow.
Fan-out / fan-inSplit one problem into focused parallel branches, then merge the results.
Semantic layerShared definitions and relationships that keep business data meaning consistent.
Trace / spanA trace is the full recorded run; a span is one operation inside it.
Semantic observabilityInspecting and monitoring the meaning and behavior of AI runs, not only technical metrics such as latency or errors.
Silent quality failureThe software works technically, but the AI still misunderstands the goal, uses the wrong tool, or gives an unacceptable result.
Generative UIAn interface where AI helps choose or populate the presentation a task needs. Prefer bounded components and predictable interaction patterns over unrestricted interface generation.
Headless architectureData, rules, permissions, and actions are accessible independently of the original UI while the source system still owns the rules.
Behavioral canaryA small set of critical eval cases run regularly to detect meaningful behavior drift.
Blast radiusHow much harm a failure could cause before someone notices and stops it.
Reversible autonomyBounded action that is automatically reversed or compensated when defined evidence shows it should no longer stand.

Questions to ask

  1. Where does this workflow actually break, and is the cause missing facts, the wrong procedure, or the process itself?
  2. How would we trace a failure back to its first bad step?
  3. Which business definitions must be fixed before AI analyzes the data?
  4. Can the model or provider change without rebuilding the authoritative workflow, and which canaries would tell us behavior changed underneath us?
  5. If this were a standing AI worker, what would it own, remember, and access, how long should its authority last, and what should trigger reversal or revocation?
  6. What evidence would we need before moving this from pilot to a standard workflow?

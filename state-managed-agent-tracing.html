Debugging an agent that found the right evidence and still got the answer wrong

I used a controlled, read-only State Question Investigator exercise to practice agent design and trace-based debugging. The useful lesson was not that I built an agent. It was learning how to tell whether a failure came from retrieval, missing context, or the agent's interpretation of evidence.

My role Product boundaries, test cases, failure judgment & fix decisionAI collaborator Agent instructions, fake dataset, trace review & implementation supportExercise Controlled fake State dataset
The setup

The agent could investigate, but it could not decide.

The Question Investigator had one job: investigate an unresolved State Question and return an evidence packet plus a suggested answer for human review. It could search mounted project material with Read, Grep, and Glob. Write, Edit, Bash, web access, Current State changes, Review approval, and Question resolution were all outside its authority.

The product boundaryAI can investigate and suggest. A person still decides what becomes authoritative.
What I tested

Five controlled cases tested more than whether the agent could find a file.

RetrievalDid it find the relevant evidence?

The cases required the agent to search Current State, open Reviews, Questions, Notes, Slack-style records, and transcripts rather than stop at the first plausible match.

InterpretationDid it preserve what the evidence actually established?

Pending proposals had to stay pending. A person's agreement could not become group approval. Conflicting evidence had to remain visible instead of being silently collapsed into a confident answer.

AuthorityDid it stop before the human decision?

The output could suggest an answer and a next step, but it could not resolve the Question or treat an open Review as accepted Current State.

This was a small learning exercise using fake project data. The five cases are not a production performance claim.

The failure

One case failed even though retrieval was correct.

What the sources saidOwnership was still under review

Priya Shah had offered to own customer support training, Devon was listed as backup, and an open Review proposed the assignment. Current State did not establish the owner yet.

What the agent saidIt promoted a proposal into a fact

The answer said Priya owned the training and implied broader acceptance. That crossed the product's authority boundary even though the supporting records had been retrieved.

What the trace showedThe first wrong step was synthesis

The trace showed the agent had found the relevant sources and recognized the open Review. The failure appeared when it combined those facts into a stronger conclusion than the evidence supported.

Diagnosis and retest

I changed the instruction at the layer that actually failed.

Retrieve correctly→Inspect trace→Locate synthesis error→Tighten authority rules→Rerun Q-103

The fix made the authority rules explicit: open Reviews are pending proposals unless independently established; one person's agreement is not group approval; conflicting evidence can support a proposed update but cannot let the agent declare Current State wrong or stale. I then reran the exact same Q-103 case. The agent correctly said ownership was not established and directed the human reviewer to the open Review instead of deciding for them.

What I learned

Read-only tools reduce action risk, not interpretation risk.

Bounded toolsPermissions are only one control

An agent can be unable to write anything and still give a dangerously overconfident interpretation. Tool restrictions and answer-quality safeguards solve different problems.

TracingTraces localize failure

The final bad answer did not reveal whether retrieval or synthesis failed. The trace let me see the sequence well enough to identify the first observable wrong step. It did not reveal hidden reasoning or provide mind-reading.

EvaluationRetest the same failure

A changed prompt is not evidence of a fix. Repeating the exact failed case made it possible to see whether the targeted change corrected the behavior without changing the test.

Product takeaway

The useful agent skill was deciding what the agent should not be allowed to conclude.

I chose to keep human approval mandatory, let the investigator search all approved project sources, show the evidence behind its suggestion, and avoid a user-facing confidence score that could create automation bias. The exercise reinforced the same State principle I use elsewhere: AI interprets, software enforces, and people authorize.

What I did vs. what AI did
My role

I chose the use case and authority boundaries, decided that evidence should be shown without a confidence score, selected and judged the test cases, identified Q-103 as an authority failure, and decided what behavior the fix needed to preserve.

AI's role

I used AI to draft the agent instructions, create the fake State dataset and answer key, help set up the controlled session, review outputs and traces, propose a targeted instruction change after the failure was localized, and verify the retest.

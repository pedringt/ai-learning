Debugging AI Systems

A failed AI check says something went wrong, not what. The same bad answer can come from retrieval, missing context, interpretation, authority handling, deterministic logic, the eval expectation or presentation. Reaching for the prompt first can fix the wrong layer. I look for the first place the system stopped matching the intended behavior, change only that layer, and check the same case again.

The rule I apply: if the behavior breaks the product rules, change the product. If it meets them and the test rejects it, change the test. If the intended behavior is unclear, settle that before changing either. A higher pass rate alone is never a reason to loosen an expectation.

Controlled State exercises and eval work on synthetic data. Evidence of the method, not production performance.

Observed behavior→Failure location→Decision→Verification
Example A · The agent’s behavior needed to change

The agent found the right evidence and still gave the wrong answer.

Observed behavior
In a controlled exercise (case Q-103), a read-only State agent investigated an open Question: who owns customer support training? It found the right records, including an open Review proposing Priya as owner. Its final answer then said Priya owned the training.
Failure location
Not retrieval. The trace showed the agent had the right sources and knew the Review was still open. The error appeared when it summarized them: a pending proposal became an established fact. That crosses State’s authority boundary, where only a person can make something official.
Decision
Change the agent’s instructions. Retrieval worked, and the agent couldn’t write anything, so the layer that failed was its reasoning about what the sources established. I made the rule explicit: an open Review is still a proposal, and one person’s offer is not a group decision. Changing the prompt was right here because the trace located the failure there, not because the prompt was the easiest thing to change.
Verification
I reran the same Q-103 case. The agent then said ownership was not established and pointed the reviewer to the open Review. I didn’t count the fix as real until that rerun passed.

Example B · The test needed to change

The answer met the product rules, and the test still failed it.

Observed behavior
In State’s update-interpretation evals, scenario review_question_answer_only gives State a note from Legal: the proposed vendor contract does not permit the disputed retention behavior. An open Question asks exactly that, and Current State says the contract review is still underway. The test expected State to answer the Question and do nothing else. State answered it and also proposed recording Legal’s finding in Current State, so the eval marked it a failure.
Failure location
The eval expectation. Legal’s answer supported the proposed update, and the update still went to a person for approval, so it met the product rules. The test was stricter than the product contract.
Decision
I reviewed the result against the product rules and revised the expectation, not the product. Answering alone, or answering plus a supported update, now both pass. I also added a check the old test lacked: a proposed update fails if it says the overall contract review is complete or approved. The test now accepts more correct answers and catches more overclaiming.
Verification
Two fixed-input tests confirm the revised grader accepts the supported update and rejects one claiming the review is complete. After the change, the scenario passed in every saved full run of the suite I checked: six runs between October 16 and November 2, each scoring all 16 scenarios with no errors.

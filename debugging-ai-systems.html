Debugging AI Systems

Working in QA taught me that a failed test is the beginning of an investigation, not the answer. That matters even more with AI, where the same incorrect response can have several different causes. I used two State exercises to work through that distinction. In one, the AI needed fixing. In the other, the test was wrong.

Observed behavior→Failure location→Decision→Verification

Controlled State exercises and eval work on synthetic data. Evidence of the method, not production performance.

The right evidence, the wrong answer

Observed
In a controlled State debugging exercise, a read-only AI agent found an open proposal naming someone as the person responsible for a project task, but answered as though the decision was final.
Where it failed
I checked the agent’s trace and found that it had retrieved the right information. The mistake happened when it interpreted that information in its answer, not when it retrieved it.
What I changed
I clarified the instructions and reran the test. This time, the agent correctly reported that responsibility hadn’t been decided.

Synthetic dataset. The full trace is in the agent tracing exercise.

When the test was too strict

Observed
In another evaluation, State behaved as intended, but the test marked it as a failure because it expected a narrower response.
Where it failed
In the test’s expectation, not in State. The evidence supported State’s update, and the update still went to a person for approval.
What I changed
I reviewed the evidence and product rules, then corrected the test to allow the valid behavior. Fixed-input tests now confirm it accepts the supported update and still rejects one that claims more than the evidence supports.

Fix the right problem

The lesson from both cases was the same: figure out what correct behavior should look like before trying to improve the score. Sometimes that means changing the system. Other times it means changing the test.

Debugging AI Systems

A failed AI check says something went wrong, not what. The same bad answer can come from retrieval, missing context, interpretation, authority handling, deterministic logic, the eval expectation, or presentation, so reaching for the prompt first can fix the wrong layer. I look for the first place the system stopped matching the intended behavior, change only that layer, and rerun the same case. The two examples below went opposite ways: one needed a product change, the other an eval change.

Example A · the product needed to change

The agent found the right evidence and still gave the wrong answer.

Observed behavior
In a controlled State agent exercise, the investigator found the relevant files and correctly recognized an open Review proposing an owner. Its final answer then presented that proposed owner as established fact.
Failure location
Not retrieval, which worked. The failure was in interpretation and authority: the final synthesis promoted a pending proposal into project truth.
Decision
Change the product: tighten the authority rule so open Reviews are explicitly pending.
Verification
The same case was rerun and behaved correctly. It had to pass again before I treated the fix as real.

This example used a controlled fake State dataset. It is evidence of the debugging method, not production performance. The full trace is in the agent tracing exercise.

Example B · the eval needed to change

Sometimes satisfying the test would make the product worse.

Observed behavior
In later State eval work, one scenario expected an answer-only action. The product answered and also proposed a State update that the evidence supported. The eval marked it a failure because the action did not match exactly.
Failure location
The eval expectation. The extra proposal was supported by the evidence and still left the decision to a person, so it met the product rules. The test was stricter than the product contract.
Decision
Revise the eval, not the product. Forcing answer-only behavior would have made the test more important than the product contract.
Verification
Product review against the product rules, not the pass rate, settled it.

The rule I applied: revise the eval when the behavior meets the product rules and the test rejects it, change the product when the behavior breaks them, and clarify ambiguous intent before changing either. A higher pass rate alone is never a reason to loosen an expectation.

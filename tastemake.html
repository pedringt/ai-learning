Tastemake

Tastemake is a recommendation experiment built around a simple idea: personalization is more useful when the system shows what it is learning, lets the user correct it, and makes those corrections matter.

The problem

Most recommenders learn from behavior without showing the user what they concluded.

I wanted to explore a different model. Tastemake still recommends books, movies, shows, and games, but it also exposes the patterns it thinks explain those reactions. The user can then confirm, narrow, weaken, or reject those patterns instead of only rating the next item.

That changed the product question from “can I make better recommendations?” to “can the user understand and shape what the system thinks their taste means?”

The product model

Item feedback becomes a hypothesis, not a permanent label.

Item feedback→Inferred pattern→User correction→Refined profile→New recommendations
Evidence vs. intentNot every action means “I like this”

Loved, Liked, and Didn’t like are evidence about something the user experienced. Save, browsing, and Not interested stay separate so convenience does not become false taste evidence.

Model visibilityThe profile is inspectable

Tastemake shows the patterns it is testing instead of hiding personalization behind a score.

User authorityCorrections change future behavior

A user can say a pattern is accurate, conditional, weak, or wrong. That correction stays distinct from the original AI inference.

Learning out loud

The most important iteration was making the learning itself visible.

Earlier versions could infer a Taste Profile, but the user still had to guess what changed after giving feedback. I redesigned that loop so Tastemake can explain the consequence of a reaction or correction.

So Tastemake changed

What that means

Future picks can lean into those qualities without assuming every similar romance will fit.

Recommendation explanations follow the same rule: show why a pick might work, which pattern is being tested, and what could still miss.

What testing changed

The product got simpler as the model got more sophisticated.

A confident missOuter Wilds exposed an over-broad “discovery” pattern. I narrowed the hypothesis instead of simply lowering a hidden similarity score.
Cold-start frictionBrowse made it easier to recognize familiar items when favorites were hard to recall, while browsing itself remained non-evidence.
Feedback overloadDetailed taste refinement moved behind progressive disclosure. The card stays simple first; deeper questions appear only when useful.
AI product quality

The model interprets and ranks. Software protects the meaning of the data.

Catalog-constrainedThe model cannot invent the whole recommendation set

Candidate eligibility comes from the catalog and software rules. The model ranks and explains within those boundaries.

Safe fallbackValid recommendations still exist if the model call fails

Catalog-based fallback behavior keeps the product usable instead of presenting low-confidence model output as trustworthy.

Regression coverageProduct rules became tests

I added automated coverage around recommendation behavior, evidence semantics, profile corrections, mobile layout, and the first learning loop.

Where I landed

The interesting part of Tastemake is not the recommendation list. It is the editable model behind it.

The candidate-retrieval layer is intentionally conventional. The stronger product experiment is above it: separating evidence from intent, showing what the system inferred, making uncertainty visible, and letting the user change the model in a way that affects what happens next.

That is the principle I would carry into other AI products: personalization becomes more useful when learning is visible, revisable, and consequential.

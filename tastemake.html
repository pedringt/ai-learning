Tastemake

Tastemake is a working product for user-editable personalization. Recommendations are the surface; the harder question is whether people can see, understand, and correct the model an AI builds of their taste.

My role Product model, UX rules, evaluation & testingAI collaborator Research, implementation, debugging & test supportStatus Working product · portfolio build

In shortTastemake shows people the taste profile an AI builds from their feedback and lets them correct it, so a correction changes what the system believes and what it tries next.

The problem

Most recommenders learn from behavior without showing the user what they concluded.

Most recommendation systems ask for a rating and move on. I wanted Tastemake to show the patterns behind its recommendations too. If it decides you like something because of atmosphere, pacing, characters, or another pattern, you can tell it whether that read is right.

The question became less about making a smarter recommendation list and more about whether the user could understand and improve the model behind it.

The product model

Feedback gives Tastemake a working theory, not a permanent label.

Item feedback→Inferred pattern→User correction→Refined profile→New recommendations
Evidence vs. intentNot every action means “I like this”

Loved, Liked, and Didn’t like come from something the user actually tried. Saving or browsing does not count as taste evidence on its own.

Visible learningThe profile shows its work

Tastemake shows the patterns it is using instead of hiding them inside a recommendation score.

User controlCorrections affect what happens next

A user can say a pattern is right, partly right, too strong, or just wrong. Tastemake keeps that correction separate from the original AI guess.

What changed

The biggest improvement was showing what actually changed.

Earlier versions could build a Taste Profile, but the user still had to guess what their feedback changed. I redesigned that part so Tastemake explains what it learned and how that will affect future recommendations.

Recommendation explanations use the same approach: why this might work, what Tastemake is testing, and what could still be wrong.

What testing changed

Testing made the product simpler.

A confident missOuter Wilds showed that Tastemake was treating “discovery” too broadly. I narrowed the pattern instead of just lowering a hidden score.
Cold-start frictionBrowse gave people another way to find familiar titles when four favorites were hard to recall. Browsing itself still does not count as taste evidence.
Too much feedback at onceI moved deeper taste questions behind the first reaction so the recommendation card stays simple unless more detail is useful.
Evidence from the build

The product had to work beyond a good-looking recommendation card.

The current version uses live model calls for two distinct AI functions: ranking recommendations and generating the Taste Profile. The surrounding product logic stays deterministic, including catalog constraints, saved-versus-tried state, and the controls that decide what evidence is allowed to influence the profile.

Live AI, bounded by softwareTwo AI functions, clear limits

Live AI ranks recommendations and builds Taste Profile hypotheses. Software still decides what counts as evidence, which catalog items are allowed, and whether model output is valid.

LatencySpeed became a product problem

Recommendation generation was taking roughly 10–16 seconds in testing, with model inference dominating the wait. At that point the delay was part of the user experience, not just a backend metric. I reduced unnecessary prompt context and changed the loading experience so the flow stayed understandable while the model was working.

Real catalogIt works across books, movies, TV, and games

Tastemake pulls from real catalog sources, then applies its own rules and stored metadata so the product is not limited to a hand-written demo set.

Regression coverageImportant rules became tests

I built coverage around recommendation quality, AI output validation, evidence rules, profile corrections, accessibility, mobile layout, and the first learning loop.

Where I landed

The recommendation engine became a test environment for an editable user model.

The product got more interesting when feedback stopped being just another hidden score. A useful correction changes the system’s explanation of what it believes, preserves where that belief came from, and affects what it tries next.

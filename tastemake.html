Tastemake

Tastemake explores what happens when users can refine not only recommendations, but the model of their taste behind them. It starts with familiar item reactions, turns those into an inferred Taste Profile, and then lets users correct what the system thinks those reactions mean.

The problem

How do you let a system learn taste without overclaiming what it knows about the person?

A typical recommender can learn that two items look similar or that someone clicked on both. I wanted Tastemake to go a step further: infer why a pattern might hold, keep that interpretation visible, and let the user correct it when the explanation is too broad or simply wrong.

What makes it different

Most recommenders let you react to items. Tastemake also lets you react to the model built from those reactions.

Item feedback→Inferred taste→Taste-model feedback→Refined profile→Better discovery
1 · Item feedbackReactions carry different meanings

Loved, Liked, and Didn’t like are evidence about experienced taste. Save and Not interested are future-intent signals and are not treated as the same kind of evidence.

2 · Taste ProfileThe system forms a working hypothesis

Patterns can span Watch, Read, and Play, while still allowing a preference to matter in one domain and not another.

3 · Taste refinementThe user can correct the interpretation

A pattern can be marked accurate, inaccurate, stronger, weaker, conditional, or limited to particular domains.

User-confirmed stateCorrection stays distinct from inference

What the user explicitly confirms is kept separate from what the AI originally inferred.

Product rules

The model is useful only if the product stays honest about evidence, intent, and uncertainty.

Evidence vs. intentNot every click becomes a claim about identity

Saving something is not the same as liking it. Browsing is not taste evidence. The software keeps those meanings separate so convenience does not weaken the model.

Constrained AIThe model does not control the whole system

Software determines eligibility, what counts as evidence, and what state can change. The model interprets, ranks, and explains within those boundaries. Invalid output falls back to catalog-based recommendations.

Profile, not personality labelPatterns are hypotheses

Tastemake avoids presenting an inference as “this is who you are.” The profile shows supported patterns that can be challenged and revised.

Learning from misses

A bad recommendation can reveal which assumption about taste was wrong.

One early model over-weighted discovery and exploration because those traits appeared in several favorites. That produced a confident but wrong prediction for Outer Wilds. The useful response was not simply “recommend less exploration.” Later testing narrowed the idea: discovery worked better when it supported narrative, stakes, character, or another clear goal.

That became a product principle. A miss should help Tastemake refine the explanation behind the recommendation, not just push a hidden similarity score in the opposite direction.

A UX tradeoff

Browse solved a cold-start problem without turning browsing into taste evidence.

The first version asked for four favorites because that gave the system a cleaner starting signal. In practice, people may struggle to recall favorites on demand. Browse lets them recognize things they already know and react from there, while preserving the rule that browsing alone does not teach Tastemake what they like.

Where I landed

The more original work is in how Tastemake learns and represents taste, not in inventing a new retrieval algorithm.

The recommendation candidate layer is still fairly conventional. Tastemake’s stronger experiment is the layer above it: separating evidence from intent, making inferred patterns visible, letting users refine the model itself, and treating recommendation misses as information about which hypothesis failed.

That shifted the project from “build a better recommender” to a more interesting question: can personalization become more useful when the user can inspect and shape what the system thinks their preferences mean?

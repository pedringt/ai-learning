How State Works

The behavioral contract for State: what each object is, what rules the system enforces, and what happens when something goes wrong or goes stale. This assumes you already know why State exists. For that, and the product decisions behind it, read the case study first.

Depth Product and system behavior, not source codeBest for Product, engineering, and technical reviewersStatus Working prototype, not in production use
01 · Overview

State maintains one current, versioned understanding of a project.

It updates only through an authorized decision, and every accepted change is recorded. The sections below describe the objects, rules, and contracts the system currently enforces.

02 · Core objects

Six object types, each with one job.

EvidenceWhat happened, was said, or was observed

Immutable. Never edited to match a later interpretation.

Current StateWhat the project currently treats as true

Versioned. Changes only through an authorized Review decision.

ReviewA consequential interpretation that needs a human decision

It may propose changing Current State, creating or resolving a Question, or leaving Current State unchanged.

QuestionA known unknown the team is tracking

Open by default. A Question can additionally be marked blocking.

HistoryThe record of accepted transitions

Before, after, reason, decision, and source, written once per accepted change.

AskA read-only, grounded query interface

Reads Current State, Reviews, Questions, History, and Evidence. Cannot modify any of them.

Question matching is not AI-driven. Text is normalized (case-folded, whitespace-collapsed) and compared for an exact match against open Questions in the same project. There is no fuzzy or semantic matching.

04 · Evidence lifecycle

Created once. Never edited. Optionally referenced.

Created from a Note, an approved Slack message, or manual entryImmutable once createdA correction creates new Evidence rather than editing the originalZero or more Reviews can reference a given piece of EvidenceNot itself a claim about what's true, only a record of what was seen
05 · Review lifecycle

Not every Review is a Current State proposal.

Review has four types: two shapes of Current State proposal (updating/retiring an existing fact, or creating one that's currently missing entirely), a Question suggestion, or a flagged uncertainty about an existing fact (state_at_risk). The two proposal shapes resolve identically; the other two each have their own resolution behavior. The decision a person makes resolves the Review, but what that decision does depends on the Review's type.

Update Current State

Accept a proposed create, update, or retire. History records the before, after, and the Evidence behind it.

Adjust, then update

A person corrects the wording before accepting. Both the original proposal and the accepted wording stay on record.

Leave Current State unchanged

The Evidence is reviewed without a Current State mutation. The Evidence stays preserved and available.

Keep tracking uncertainty

On a state_at_risk Review, this creates or links a Question instead of changing Current State.

Create Question

A Question-suggestion Review requires human authorization before the Question is created or linked.

Superseded proposal: newer Evidence can replace an older pending proposal before it's reviewed. The Review stays open; the proposal, not the Review, changes state.Stale proposal: accepting is blocked if the target Current State item changed since the proposal was createdA Question-suggestion or uncertainty Review can also be dismissed, resolving the Review without creating or linking a QuestionMultiple proposals from the same Evidence are bundled into one Review and decided together, not one at a time
06 · Question lifecycle

Open, optionally blocking, resolved by reviewed Evidence, or stopped.

Created open by defaultBlocking is set explicitly, never inferred from wordingA state_at_risk Review's "keep tracking" decision creates or links a Question, rather than resolving oneResolved as part of the same Review that handles the answering Evidence, not a separate stepAnswering a Question does not require a Current State changeCan be stopped manually when no longer worth tracking, without being resolvedA new Question is deduplicated by exact normalized-text match against open Questions in the same project, before it's created
07 · Current State rules

Each Current State item has one active, versioned value.

Versioned; every accepted change increments the versionOnly changes through an accepted ReviewSupports three operations: create, update, retireScoped to a project and an areaA stale write (based on an outdated version) is rejected, not merged or overwritten
08 · History rules

An append-only log of accepted transitions.

Written only when a Review is acceptedNever edited or removed after being writtenRecords before, after, reason, decision, and source togetherNot a duplicate or cache of Current State's present values
09 · Ask contract

Reads across State. Writes nothing.

01

Reads

Accepted Current State, pending Reviews, open Questions, and relevant Evidence and History, bounded by the application rather than the full dataset.

02

Returns

An answer with accepted facts, pending Reviews, and open Questions kept in visibly separate categories, never merged into one undifferentiated summary.

03

Cannot do

Create, accept, or modify a Review, Question, or Current State. A query that reads like an instruction is redirected to Add Evidence instead of acted on.

11 · Failure and stale-data behavior

Reference table: situation to system response.

Situation
System response
An AI interpretation looks wrong or unsupported
Stays a pending Review. Nothing reaches Current State without an accepted decision.
A proposal is stale (Current State changed since it was created)
Accept is blocked on a version check. The client is told to refresh and review again.
New evidence conflicts with an existing pending proposal
The older proposal is marked superseded rather than left open alongside the new one.
The AI provider fails or times out
The request fails closed with an error, not a guess or a partial unlabeled answer.
Model output doesn't match the expected schema
Rejected by validation before it reaches the client.
12 · Testing and evals

Deterministic tests, realistic QA, and AI evals.

Backend and frontend behavior is covered by several hundred deterministic tests (authority checks, version conflicts, duplicate detection, response shape), supplemented by hands-on QA against realistic, messy input and by evals that judge Ask's grounding and the review pipeline's consequentiality calls against expected outcomes rather than just checking for a valid response. See docs/evals/ for the PM-facing eval registry and state-project-complete/eval/ for the executable eval code.

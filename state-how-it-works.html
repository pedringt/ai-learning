How State Works

A closer look at State's product model, system rules, AI behavior, and the safeguards that keep AI interpretation from becoming project truth on its own. Start with the case study for why State exists. This page is for how it actually behaves.

Depth Product and system behavior, not source codeBest for Product, engineering, and technical reviewersStatus Working prototype, not in production use
State at a glance

State keeps one maintained answer to what a project currently treats as true.

Most AI systems that touch project information are already good at finding and summarizing it, through enterprise search, retrieval, context engineering, or agent memory. State works on a narrower problem next to that one. When information changes, conflicts, or goes stale, what should the team and its AI treat as true right now? State's answer is to maintain one current understanding rather than reconstruct one from raw history every time someone, or an AI, needs an answer.

The core ideaNew information does not become trusted context on its own. A person has to authorize it before it becomes Current State.
The product model

Six objects, each with one job.

Everything in State is one of six object types. Each has a narrow job, and together they keep new information, AI's read on it, and the team's accepted understanding from blurring into one thing.

EvidenceWhat happened, was said, or was observed

Notes, meeting recaps, decisions, corrections, and approved Slack messages all become Evidence. It's a historical record. It does not change on its own and is never edited to match a later interpretation.

Current StateWhat the project currently treats as true

A versioned set of facts the team relies on right now. It only changes through an authorized Review decision, never automatically because new Evidence arrived.

ReviewAI's read on what evidence means, pending a decision

When Evidence looks consequential, AI proposes what it might mean: create a fact, update one, or retire one. The Review holds that proposal until a person accepts it, adjusts it, or leaves Current State unchanged.

QuestionA known unknown the team is tracking

Not everything is a fact waiting to be confirmed. A Question tracks something the project doesn't yet know. Some Questions block related work; most don't.

HistoryThe record of accepted transitions

Every time Current State actually changes, History keeps the before, after, reason, decision, and source together. It's a record of what changed and why, not a second copy of the current facts.

AskA grounded read across everything above

Ask answers questions using accepted Current State, pending Reviews, open Questions, and History, keeping them clearly labeled as separate kinds of information. Ask cannot change any of them.

How information moves

Nothing skips the queue on its way to becoming a fact.

Source or note→Evidence→AI interpretation→Proposed change→Human decision→Current State→History

Every step is optional to advance past except the human decision. Evidence can sit without a Review if nothing about it looks consequential. A Review can be left unchanged, which preserves the Evidence without moving Current State. Only an accepted decision reaches Current State, and only then does it get a History entry.

The authority model

AI can interpret. It cannot decide what becomes true.

AI interprets→Software enforces→People authorize
AI's jobRead Evidence, propose meaning

AI drafts what new Evidence might mean for Current State, and drafts answers in Ask. It never has a path that applies a change by itself.

Software's jobEnforce the rules a model shouldn't have to get right

Structural validation, version checks, and duplicate detection run in code, not in a prompt. A proposal that doesn't meet the contract never reaches a person to decide on.

People's jobAuthorize what actually becomes true

Only an accepted Review decision changes Current State. A person can also adjust the wording first; the original AI proposal stays on record either way.

New evidence doesn't become Current State because AI found it convincing. It becomes Current State because a person said so.
Reviews

A Review is a checkpoint, not an approval.

Requiring a decision exists because a technically valid AI interpretation can still be wrong for the project, confidently filling in something nobody actually decided. A Review holds the proposal open until a person looks at it.

Accept

The proposed change becomes Current State exactly as AI proposed it. History records the before, after, and the Evidence behind it.

Adjust, then accept

A person can correct the wording before it becomes Current State. Both the original AI proposal and the accepted wording stay on record, so History and Ask can explain the difference later.

Leave unchanged

Current State doesn't move. The Evidence is still preserved and available; it just wasn't enough on its own to justify a change.

Superseded or stale

If newer Evidence produces a better proposal for the same fact before anyone reviews the first one, the older proposal is marked superseded instead of leaving two conflicting proposals open. If Current State already changed by the time someone tries to accept an older proposal, State blocks it and asks them to refresh and review again, rather than silently overwriting a newer decision.

When more than one proposed fact comes from the same Evidence, they're bundled into one Review and decided together, not accepted one at a time.

Questions

Not knowing something yet is different from being wrong.

Open vs. blockingMost Questions don't stop anything

An open Question tracks something unresolved. A blocking Question additionally flags that related work shouldn't proceed until it's answered. That distinction is set explicitly, not guessed from wording.

Resolving a QuestionNew evidence can answer it directly

When Evidence addresses an open Question, State can resolve it as part of the same Review that handles the Evidence, instead of a separate step later.

Answered isn't the same as changedAnswering a Question doesn't require changing Current State

A Question can be fully answered, including with a plain "no," without Current State needing to move at all. The two are tracked and decided separately.

Avoiding duplicatesThe same unknown doesn't get tracked twice

If a newly proposed Question matches one already being tracked, State links to the existing one instead of creating a duplicate.

Current State and History

An answer generated fresh every time can't tell you when something actually changed.

Regenerating a summary

Depends on what happened to be pulled into context that specific time. Two summaries of the same project can disagree, and neither is exactly wrong, they just surfaced different things. There's a record of what got said, but not a durable one of what the project decided.

Maintaining Current State

One version exists at a time, and it only moves when a person authorizes the change. History keeps the actual transitions, so the project can explain not just what's true now but when it became true and why.

Ask

Ask answers questions. It doesn't make decisions.

01

What it reads

Accepted Current State, pending Reviews, open Questions, and relevant Evidence and History, gathered and bounded by the application rather than handed everything that exists.

02

Typical uses

Preparing for a meeting, catching up on what changed, checking whether something has actually been decided, or asking why a past decision went the way it did.

03

What it can't do

Ask is read-only. It can't create, accept, or change a Review, Question, or Current State. A question that reads like an instruction gets redirected to Add Evidence instead of acted on.

Where AI is used, and where it isn't

Anything that has to be right every single time lives in software.

Where AI is used
Interpreting new EvidenceProposing Current State changesAsk & synthesisMatching a new Question to an existing one
Where deterministic software is used
Schema & type validationAuthority checksVersion checks before a change appliesAtomic, all-or-nothing writesDuplicate detectionStripping internal ids from AI-facing text

AI gets the parts where judgment and language genuinely help. Everything else, the parts that need to be correct every time rather than usually, stays in code.

Failure handling

Most failures are handled before they reach Current State.

Situation
What happens
An AI interpretation looks wrong or unsupported
It stays a pending Review. Nothing reaches Current State without a person accepting it.
A proposal goes stale because Current State changed since it was created
The accept is blocked. The person is asked to refresh and review again instead of silently overwriting a newer decision.
New evidence conflicts with an existing pending proposal
The older proposal is marked superseded instead of leaving two contradictory proposals open.
The AI provider fails or times out
Ask fails closed with a clear error rather than guessing or returning a partial, unlabeled answer.
The model returns output that doesn't match the expected structure
The response is rejected before it reaches the product, rather than shown as-is.
Testing and evals

Passing tests and being right are two different bars.

Deterministic coverageHundreds of backend and frontend tests

Regression and behavior tests cover the rules that must never bend: authority checks, version conflicts, duplicate detection, and the shape of every response.

Realistic QAMessy, real-shaped input

Clean fixtures miss problems that only show up in long, ambiguous notes. Hands-on testing with realistic evidence surfaced issues automated tests didn't catch.

AI evalsJudged, not just executed

Ask's grounding and hedging behavior, and the review pipeline's judgment about what's consequential, are checked against expected outcomes, not just checked for a valid response.

Current boundaries

What this is, and isn't, today.

State is a working prototype I built and use to test the idea, not a system a real team has run over time. Being direct about the current limits:

No multi-user roles or permissionsNot load-tested at real team scaleA known slow query pattern affects project switching under PostgresProject areas aren't fully scoped per project at the schema level yetAsk's generated prose occasionally has minor grammar issues

These are documented, not hidden. They're the honest reason I call State a prototype rather than a finished product.

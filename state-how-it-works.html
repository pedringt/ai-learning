How State Works

The behavioral contract for State: what each object is, how they relate, and what happens when something goes wrong or goes stale. This assumes you already know why State exists. For that, read the case study first.

Depth Product and system behavior, not source codeBest for Product, engineering, and technical reviewersStatus Working prototype, not in production use
01 · Overview

State maintains a current, versioned understanding of a project.

Consequential changes require human authorization. The sections below describe the resulting behavioral contract: the objects, how they relate, and the rules the system enforces.

Proposal state is separate from the Review decision above:

Stale: the target Current State item changed since the proposal was created, so acceptance is blocked
Superseded: newer Evidence updates the same Review with a replacement proposal for the same State item, so the older pending proposal is superseded. Unrelated open Reviews are never affected.
Multiple proposals from the same Evidence are bundled into one Review and decided together, not one at a time

Answering a Question does not necessarily change Current State

If the accepted State wording is materially adjusted from the AI's proposal, linked Questions remain open for separate judgment

History is written when an accepted Review produces an actual Current State transition. Question creation, a no-op adjustment, or an exact duplicate create do not manufacture a History entry.

Current State doesn't guarantee semantic uniqueness across differently worded items; it version-checks each item individually.

What happens when something goes wrong.

System response

12 · Known limitations

Current, documented limits.

No multi-user roles or permissions
Not load-tested at real team scale
A known slow query pattern affects project switching under Postgres
Project areas aren't fully scoped per project at the schema level yet
Ask's generated prose occasionally has minor grammar issues

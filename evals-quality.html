Meridian · design focus

Risk-based evals change what gets tested

The eval suite reflects the guardrails: high-risk categories (financial, security, account changes) are included to verify recognition, no-draft behavior, and correct human routing. They are excluded only from draft-quality scoring because the correct behavior is not to draft. Eval design follows from the system design, not the other way around.

  • Classification accuracy matters most for routing safety; misclassifying a refund request into "general inquiry" is a costly failure mode.
  • Retrieval quality is gated on having real knowledge sources; simulator evaluation exposed staleness and conflicts that prompt engineering can't fix.
  • Confidence and observable evidence determine whether a draft reaches the normal mandatory-review path or is flagged with additional context for the reviewer; nothing auto-sends during the pilot.

Harborstone · transfer case

Evals for human-reviewed extraction, not fully automated extraction

Because the Harborstone pilot deliberately retained human verification, the eval criteria measure extraction quality that a human can efficiently review, not perfect extraction.

  • Recall matters more than precision for line-item extraction (missing a row is expensive, but an extra field can be ignored).
  • Field-level accuracy differs by field type: dollar amounts need exact matches, whereas description text can tolerate minor OCR variation if human verification catches errors.
  • Ambiguous documents and business-rule exceptions are tested separately from model extraction, because solutions differ (source cleanup vs. prompt refinement).

Closing reflection

What transfers across the cases

The repeated skill is not "running evals" in the abstract. It is reasoning about what quality means in context (for whom, at what step, relative to what alternative), then designing specific tests that would catch failure modes that matter, while ignoring noise that doesn't.
